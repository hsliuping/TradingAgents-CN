## 1. 背景

在原有多 Agent 分析模式下，系统虽然已经具备了多角色协作能力，但其扩展方式主要依赖：

- 为新角色重写代码
- 为新场景补充配置
- 为新流程重新连接工具、提示词和上下文

这种模式在早期是可以接受的，因为它有助于快速验证：

- 多 Agent 协作是否有效
- 不同角色分工是否能提升分析质量
- 分析流程是否能比单次回答更完整

但当 v4.0 的目标开始转向“长期投研陪伴工作台”时，这种扩展方式会逐步暴露出三个问题：

1. **扩展成本高**：每增加一个角色或流程，都需要开发者继续拼装系统。
2. **学习成本高**：用户难以理解内部角色、配置和流程切换逻辑。
3. **演进方式不对**：系统的成长更像工程堆叠，而不是统一能力底座上的持续演进。

因此，v4.0 需要把一个关键能力重新定义清楚：

**多 Agent 仍然保留，但它不应再主要表现为“手写流程集合”，而应升级为“统一的自定义 Agent 团队底座”。**

---

## 2. 核心定位

### 2.1 自定义 Agent 团队是什么

这里的“自定义 Agent 团队”，不应理解成让用户自己像开发者一样去造一套 Agent 平台。

更准确的定义应是：

**系统提供统一的角色化能力底座，让用户和系统都可以围绕“团队角色、职责分工、记忆边界、技能权限、任务模板”来组织投研流程。**

它是：

- 长期投研陪伴工作台的过程引擎
- 用户私有研究资产的动态执行层
- 多阶段投研闭环的角色协调层

它不是：

- 通用 Agent 开发平台
- 面向用户暴露大量底层配置的工作流编排器
- 无边界的自成长系统

### 2.2 它在 v4.0 中的位置

如果把 v4.0 看成三层结构，那么自定义 Agent 团队对应的是中间层：

1. **产品目标层**：长期投研陪伴工作台
2. **能力组织层**：自定义 Agent 团队
3. **演进机制层**：受控 Skill 增长与审核式能力升级

这意味着：

- 前台产品价值不应直接讲成“我们有很多 Agent”
- 但后台能力组织必须逐步从“流程写死”转向“团队化组织”

---

## 3. 为什么 v4.0 需要这一层

### 3.1 需要降低研发扩展成本

后续如果继续围绕：

- 跟踪
- 分析
- 计划
- 执行记录
- 复盘
- 周期整理

来建设长期工作台，就必然会出现越来越多的角色化任务。

如果每个角色都继续走“写一个新 Agent、补一套新配置、接一条新流程”的模式，系统复杂度会快速失控。

### 3.2 需要降低用户理解成本

用户不需要理解：

- 这个 Agent 类和那个 Agent 类有什么区别
- 这次为什么切到另一条工作流
- 为什么要额外配置很多内部参数

用户更容易理解的是：

- 现在由哪几个研究角色在协作
- 每个角色负责什么
- 它们记住什么
- 它们最后把什么沉淀进我的研究系统

### 3.3 需要让长期陪伴真正“运转起来”

静态的研究库和知识底座只能解决“能不能存”“能不能查”的问题。

但长期陪伴工作台还需要解决：

- 谁在跟踪变化
- 谁在整理计划
- 谁在提醒执行偏差
- 谁在做复盘总结
- 谁在建议沉淀为长期资产

这就需要一个稳定的角色组织层。

## 4. 角色模型建议

### 4.1 角色不是“人设”，而是职责单位

在 TradingAgents 中，角色首先应被定义为职责单位，而不是聊天产品里的性格人设。

一个角色应至少回答以下问题：

- 它负责什么任务
- 它的输入来源是什么
- 它的输出目标是什么
- 它应调用哪些技能
- 它应记住哪些内容
- 它在哪些场景下参与协作

### 4.2 建议的基础角色类型

v4.0 更适合先围绕投研闭环定义角色，而不是围绕技术组件定义角色。

建议优先考虑以下几类：

1. **跟踪角色**
   - 负责变化发现、信息整理、异常提示、观察项更新

2. **分析角色**
   - 负责基本面、行业、主题、风险、估值等维度的判断辅助

3. **计划角色**
   - 负责把当前判断整理为候选计划、观察条件和风险边界

4. **执行记录角色**
   - 负责把用户的真实动作、执行偏差和原因记录下来

5. **复盘角色**
   - 负责回看事实变化、当时判断、执行结果和纪律偏差

6. **沉淀角色**
   - 负责把一次任务中的高价值内容转化为研究卡片、观点、规则或关系更新建议

### 4.3 角色的表达维度

每个角色可以进一步被以下维度刻画：

- **职责范围**：负责哪些环节
- **立场视角**：偏审慎、偏进攻、偏中性、偏证据导向
- **表达风格**：简洁、结构化、解释型、提醒型
- **证据偏好**：更重视事实、趋势、规则、关系还是历史案例
- **升级权限**：只能建议，还是可以形成待确认沉淀

这里的“性格”更适合被限制在这些与任务相关的维度里，而不是做成泛化聊天人格。

## 5. 记忆边界建议

### 5.1 记忆不是越多越好，而是越清楚越好

v4.0 里的 Agent 团队，不应追求“所有角色都尽可能记住更多内容”。

更合理的原则是：

- 角色只记与自己职责相关的内容
- 长期记忆要有来源、时间和范围
- 不能把临时上下文、正式资产和用户立场混在一起

### 5.2 建议采用四层记忆边界

#### A. 当前任务记忆

只服务于本次任务执行，例如：

- 当前问题
- 本次工具结果
- 当前阶段的中间判断

特点：

- 生命周期短
- 不自动进入长期资产

#### B. 对象跟踪记忆

围绕某个标的、行业、主题的连续记忆，例如：

- 过去的跟踪结论
- 最近几次变化点
- 历史关注风险
- 观察项变化

特点：

- 服务于长期跟踪
- 应按对象组织

#### C. 用户偏好与行为记忆

围绕用户长期习惯的连续记忆，例如：

- 关注风格
- 常见偏差
- 常用判断框架
- 常见纪律问题

特点：

- 服务于个性化陪伴
- 不能未经确认直接上升为正式规则

#### D. 正式研究资产记忆

这是已经进入研究库的正式内容，例如：

- 研究卡片
- 用户观点
- 用户规则
- 关系图谱节点和关系

特点：

- 应由系统稳定承接
- 角色只能读取或提出更新建议，不能默认越权改写

### 5.3 不同角色应有不同记忆权限

例如：

- 跟踪角色更适合读取对象跟踪记忆
- 计划角色更适合读取用户规则和历史计划
- 复盘角色更适合读取执行记录和历史观点
- 沉淀角色更适合读取当前任务结果并生成候选资产升级建议

这样能避免所有角色都读写同一堆记忆，造成边界混乱。

## 6. 技能权限建议

### 6.1 技能不应无差别开放给所有角色

如果所有角色都能任意调用所有技能，会出现两个问题：

1. 团队分工失去意义。
2. 行为边界难以控制。

因此，更合理的方式是：

- 每个角色有自己的技能包
- 技能包与职责范围一致
- 高风险或高影响技能要受到更严格约束

### 6.2 技能包建议按角色和阶段组织

例如：

- 跟踪角色：信息聚合、变化比较、对象摘要类技能
- 分析角色：财务、估值、行业、概念关系、事件解释类技能
- 计划角色：计划结构化、观察条件整理、风险清单生成类技能
- 复盘角色：事实回看、偏差对照、规则违背识别类技能
- 沉淀角色：卡片提炼、观点抽取、规则候选生成类技能

### 6.3 技能调用结果应能回流到系统结构层

技能不应只为“回答得更完整”服务，还应帮助系统完成：

- 对象更新
- 计划补充
- 复盘记录
- 研究卡片生成建议
- 规则升级建议

这时技能才真正成为工作台的一部分，而不是单次回答工具箱。

## 7. 协作方式建议

### 7.1 协作目标不是“让更多角色发言”，而是让流程更完整

Agent 团队的价值不在于角色数量，而在于：

- 是否减少遗漏
- 是否提升连续性
- 是否帮助用户进入下一阶段
- 是否帮助长期资产沉淀

### 7.2 建议优先采用三种协作模式

#### A. 串行协作

适用于闭环阶段明显的场景，例如：

- 跟踪 → 分析 → 计划 → 复盘

优点：

- 容易解释
- 容易控制边界

#### B. 并行协作

适用于同一阶段的多视角补充，例如：

- 基本面、行业、风险三个角色并行分析

优点：

- 提升效率
- 保持多视角完整性

#### C. 汇总协作

适用于把多个角色结果收束为下一步候选动作，例如：

- 汇总后形成候选计划
- 汇总后形成候选沉淀动作

优点：

- 有助于回到用户可理解的单一界面输出

### 7.3 不建议优先做成完全开放式编排平台

在 v4.0 阶段，更适合：

- 先提供专项任务模板
- 再提供少量可调整角色
- 最后再逐步开放高级定制能力

而不是一开始就让用户面对完整的 Agent 编排系统。

---

## 8. 面向用户的产品表达建议

### 8.1 用户看到的应是“研究团队”，不是底层实现细节

前台更适合表达为：

- 当前由哪些研究角色参与
- 每个角色负责什么
- 它们分别看到了哪些证据
- 它们最终建议了什么下一步动作

而不是表达为：

- 当前触发了哪些内部 Agent
- 当前使用了哪些底层配置
- 当前切换到了哪条内部工作流

### 8.2 建议的前台概念

用户更容易理解的概念包括：

- 我的研究团队
- 当前任务模板
- 参与角色
- 团队记忆范围
- 团队建议动作
- 是否沉淀到研究库

### 8.3 不建议暴露太多底层词汇

例如以下词汇更适合作为内部实现语言，而不适合作为用户主语言：

- 节点配置
- Agent 类
- Prompt 绑定
- 工具路由细节
- 工作流内部拓扑

## 10. 本文结论

对于 v4.0，建议判断如下：

1. **多 Agent 方向应继续保留**，因为长期投研陪伴工作台需要角色化协作。
2. **原有手写多 Agent 扩展方式不应继续作为基础形态**，因为它扩展成本高、学习成本高，也不利于长期演进。
3. **更合理的下一阶段基础能力，是统一的自定义 Agent 团队底座**，按角色、记忆、技能、协作方式来组织能力。
4. **角色首先是职责单位，而不是聊天人格**。
5. **记忆必须有边界，技能必须有权限，协作必须有模板，升级必须有审核。**
6. **前台产品表达应是“研究团队”和“角色分工”，而不是底层工作流和代码装配。**

因此，v4.0 更合理的方向不是继续为每个场景手写更多 Agent，而是：

**把多 Agent 能力升级为统一的 Agent 团队底座，让长期投研陪伴工作台真正拥有稳定、可扩展、可理解的过程引擎。**
