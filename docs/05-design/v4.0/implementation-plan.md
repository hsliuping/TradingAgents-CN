## 1. 目标与范围

**一句话目标**：把"单次分析工具"升级为"长期投研陪伴工作台"——补全五环旅程（跟踪→分析→计划→执行[模拟]→复盘），让研究过程沉淀为用户私有资产。

v3.0 引擎层已基本建成（P0 五项与平台化能力全部落地，见映射文档 §2.1），v4.0 的真实剩余工作收敛为泳道二（产品闭环）的五个工作项，按依赖排为四个阶段。

### 1.1 明确不做（继承 R1-R8 修订决策）

| 不做的事 | 依据 |
|---|---|
| 执行环做厚（实盘对接、替代券商/行情工具） | R4：工作台定位为决策与研究驾驶舱，执行保持薄（模拟盘+持仓导入） |
| 自建公司知识图谱层 | R3：公司库由配套项目 CRKB 承载，TA-CN 经 REST+MCP 消费 |
| 平台化能力扩张（AI 工作流/Skill 自动生成等） | triage 结论：已建成，维持内部化/管理员工具定位，不再投入 |
| 网站版交付形态建设 | 跟随商业化节奏，不作为能力开发项 |
| AI 介入深度 A/B/C/D 档 | 延后至资产层之后（v4.0 后期或 v4.1，注意与分析深度区分 R8） |
| 市场验证裁判、methodology skill、错误库第一期 | 属泳道三/四（认知内核与进化机制），另行规划；但 Phase 2 的沉淀动作是其入口，结构上预留衔接 |

## 2. 阶段计划

### Phase 1 · 计划环入页（五环闭环）

| 项 | 内容 |
|---|---|
| 目标 | `trading_system`（交易计划）接入股票详情页，补全第五环，五环旅程完整 |
| 现状 | 交易计划为独立模块，后端已存在；详情页操作区无计划入口（映射 §2.2） |
| 范围 | ① 详情页（`Stocks/Detail.vue`）操作区增加"计划"入口：创建/查看/更新该标的的计划；② ResearchFlow 步骤条加入计划环的状态流转；③ 智能助手上下文装载计划模块（AssistantHero 预置旅程式问题）；④ 计划与持仓/复盘标签的联动入口 |
| 前置依赖 | 无（后端已存在，纯整合工作，范围最小） |
| 验收 | □ 详情页五环旅程完整可见 □ 从详情页可创建并查看该股计划，状态流转正确 □ 助手能基于计划上下文回答"我在这只股票上的计划是什么" □ 单测 + 前端 type-check/build 通过 |

### Phase 2 · 研究资产层（沉淀动作 + 我的研究库）

| 项 | 内容 |
|---|---|
| 目标 | 沉淀成为一等动作：用户在旅程任意环节可一键沉淀；"我的研究库"承接资产 |
| 范围 | ① 三库数据模型（决策/错误/复盘，落在 MongoDB + mem0 检索层之上；公司库不自建，见 Phase 3）；② 详情页各环出口的一等沉淀动作——决策记录（买/不买/观察 + 理由）、复盘教训→错误模式、研究卡片；③ "我的研究库"页面 MVP（以原型 `library.html` 为基线）：列表/按类型与标的筛选/详情查看；④ 存量导入源打通（收藏/标签/报告/复盘案例） |
| 产品契约 | 沿用原型 v2 契约：草稿默认不入库；AI 输出是"草稿"必须确认后入库；每条资产带来源标记 |
| 前置依赖 | 设计前置任务：mem0 / 四库 / CRKB 职责边界图（映射 §6 待办，Phase 2 启动前完成） |
| 验收 | □ 旅程任一环可一键沉淀且研究库可见 □ 研究库筛选/检索可用 □ 至少两类存量数据源可导入 □ 资产导出含"AI 生成，不构成投资建议"标识（合规） □ 单测 + type-check/build 通过 |

### Phase 3 · CRKB 接入（公司库 + 证据链）

| 项 | 内容 |
|---|---|
| 目标 | TA-CN 作为消费方接入公司研究知识底座，补齐公司维度客观知识与证据回溯 |
| 现状 | CRKB 已 Docker 部署、API 契约 v1.0 冻结（2026-06）；TA-CN 侧接入未完成 |
| 范围 | ① REST + MCP 客户端（配置化接入地址）；② 公司主档/结构化事实/图谱查询接入详情页基本面上下文；③ 证据回溯为报告引用供源；④ CRKB 不可用时优雅降级（明示"该数据未获取"，禁止估算补位——数据纪律） |
| 前置依赖 | CRKB 接入排期与 Phase 1/2 进度确认（映射 §6 待办） |
| 验收 | □ 详情页基本面模块展示 CRKB 结构化事实与来源链接 □ 助手可引用公司库回答基本面问题 □ 断连时功能降级不报错 □ 集成边界符合 CRKB `integration-with-tradingagentscn.md` 契约 |

### Phase 4 · 事实-观点-规则分层呈现

| 项 | 内容 |
|---|---|
| 目标 | 报告前台让用户看得见"哪些是事实、哪些是观点、哪些是规则" |
| 范围 | ① 报告组件按 事实/观点/规则 分块渲染：类型标签 + 观点附置信度 + 事实附证据链接（CRKB/数据源）；② 沉淀动作与分层结构对齐（不同内容类型沉淀到对应库，参照 `facts-opinions-rules-presentation.md`）；③ 金融 schema（concept/metric/method/verifier，示例已起草于 `financial-schema-examples/`）作为规则层的数据结构基础 |
| 硬前置 | **泳道一 P0"裁判节点结构化输出"**（Research Manager / Risk Judge 输出 JSON Schema：结论/置信度/分歧点/关键论据）——分层的眼睛；建议与 Phase 2/3 并行推进引擎侧改造 |
| 验收 | □ 报告页每块内容有类型标签 □ 观点块附置信度 □ 事实块可溯源 □ AI 生成标识保留 □ 单测 + type-check/build 通过 |

## 4. 分支与工程流程

- 从当前基线（`v3.6-community` @ `e67688a4b`）新建 **`v4.0`** 开发分支，v4.0 全部阶段在此分支进行；里程碑节点合入主干并打 tag。
- 开发环境继续沿用 `start_dev.ps1`（v3.0 端口组：Mongo 27019 / Redis 6381 / 后端 8002 / 前端 3002）；CRKB 为独立部署，接入地址走配置。
- 每阶段交付物：后端单测（`env/Scripts/python.exe -m pytest`）+ 前端 `npm run type-check && npm run build`（Windows 本地 npm，禁 WSL）+ 阶段验收清单逐项确认。

## 5. 跨泳道依赖关系

```
泳道一（引擎）裁判结构化输出 ──→ Phase 4 分层呈现（硬前置）
Phase 2 沉淀动作 ──→ 泳道三 错误库第一期入口（结构预留）
CRKB 结构化事实 + 证据回溯 ──→ Phase 4 事实层引用（Phase 3 先行）
```

泳道一 P0 四项（深度档位打通/裁判结构化输出/分析师并行化/Prompt Caching）属引擎升级线，建议与 v4.0 阶段并行推进，其中"裁判结构化输出"最晚须在 Phase 4 启动前完成。

## 6. 风险与待确认事项

| # | 事项 | 影响 | 处理 |
|---|---|---|---|
| 1 | CRKB 排期未确认（映射 §6） | Phase 3 无法启动；Phase 4 证据溯源缺数据源 | Phase 2 期间确认；若延迟，Phase 4 的证据溯源先降级为数据源标注 |
| 2 | 付费用户访谈结论（映射 §6） | 若"避免犯错"是付费动因，错误库（泳道三）提前 | Phase 2 的决策/错误沉淀结构天然衔接，可平滑提前 |
| 3 | mem0/四库/CRKB 职责边界图未定 | Phase 2 数据模型设计输入缺失 | 列为 Phase 2 启动前的前置任务 |
| 4 | v3.0 尚处 `3.0.0-beta.4`，未发正式版 | 版本叙事与发布节奏 | 产品决策：本计划按直接进入 v4.0 编制；若需先发 v3.0 GA，M1 顺延 |
| 5 | AI 介入深度分档延后 | 功能完整性 | v4.0 后期或 v4.1 评估，不阻塞主线 |
