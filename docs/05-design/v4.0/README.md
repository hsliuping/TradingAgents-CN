## 1. 目录定位

`docs/design/v4.0/` 用于集中沉淀 TradingAgents 在 v4.0 阶段的产品设想与业务设计，重点讨论：

- 长期投研陪伴工作台的产品目标与交付形态
- 自定义 Agent 团队作为能力组织底座的定位
- Cognee 在知识与长期记忆架构中的角色
- 用户私有研究资产的承接与沉淀

当前可以把 v4.0 的整体结构先收敛为三层：

1. **产品目标层**：长期投研陪伴工作台
2. **能力组织层**：自定义 Agent 团队
3. **演进机制层**：受控 Skill 增长与审核式能力升级

这里的文档以**业务与概念设计**为主，不以具体技术实现为目标。

## 4. 当前结论摘要

基于目前的讨论，v4.0 的核心收敛方向可以概括为：

- 长期投研陪伴工作台是 v4.0 的产品目标与最终交付形态
- 自定义 Agent 团队是支撑这一目标的能力组织底座，不应再继续依赖手写 Agent 与高耦合流程扩展
- 受控 Skill 增长是能力演进机制：系统发现缺口、报告建议、由主人或管理员审核后新增能力，而不是无监督自主生成
- TradingAgents 不是自动交易系统，也不是万能金融百科
- 它更适合作为面向个人投资者的长期投研陪伴系统
- AI 是核心能力引擎，但产品价值不能主要建立在模型本身
- AI、系统、用户三者需要有清晰边界：AI 提供增强，系统承接结构，用户保留主权
- AI 在不同流程阶段应有不同介入深度：跟踪可更积极，执行必须更克制
- 分析流程优化和提示词优化仍然重要，但应逐步从产品主轴退到能力底座与质量保障层
- 原有多 Agent 分析流程的问题不在于多 Agent 本身，而在于过度依赖代码重写与复杂配置，不适合作为长期演进基础形态
- 下一阶段更合理的方向，是把多 Agent 能力升级为角色化、模板化、可控演进的统一 Agent 团队系统
- 选股可以作为前台入口价值，但必须被设计成候选发现、可解释筛选与长期跟踪接入能力，而不是黑盒荐股器
- `v3.0` 的能力应优先继承“助手入口化、选股前台化、通知统一化、数据资产化、边界清晰化”，弱化“自动造工作流、自动长 Skill、平台化扩张”
- TradingAgents 不应把自己做成缩水版金融终端、AI 量化平台或投资社区，而更应成为个人投资者的长期投研工作台
- 面向大众用户，TradingAgents 的默认交付形态应逐步从本地部署转向网站工作台；App 更适合作为陪伴端，本地版则保留为高阶专业与私有化形态
- 从项目发展阶段看，TradingAgents 已进入早期商业验证阶段；当前重点应从“继续证明有人关注”转向“理解为什么付费、优化留存、降低交付门槛并建立可复制增长系统”
- 统一的投研知识底座，比单纯做金融微调模型更优先
- 事实、观点、规则的边界，不仅要在后台清楚，也要在前台让用户看得见
- Cognee 不应替代 Mongo 或 RAG，而应作为关系知识、长期记忆、变化跟踪层
- 用户私有研究资产应被视为一等资产，而不是附件
- 产品未来应逐步从“单次分析入口”转向“长期跟踪、过程闭环、认知沉淀”的工作台形态

### 2026-09 现状修订（基于代码核验）

上述结论中“应继承/应弱化”的判断已按代码现实复核，需补充：

- **“助手入口化、选股前台化、通知统一化、数据资产化、边界清晰化”五项已全部实现**，不再是待办
- **建议弱化/后置的平台化能力（AI 工作流生成、Skill 自动生成、回测、Agent 工坊、执行轨迹）也已实现**，维持“内部化/管理员工具”定位即可，不再投入扩张
- **股票详情页已成为五环旅程的单股载体**（跟踪→分析→执行[模拟]→复盘四环已整合，智能助手为跨环粘合层）
- v4.0 的**真实剩余工作收敛为三件事**：计划环入页（`trading_system` 接入详情页旅程）、研究资产层（“我的研究库”）、事实-观点-规则的前台分层呈现
- **执行环定位为“做薄”**：工作台是决策与研究驾驶舱，不追求替代券商/行情工具（修订 R4）
- **配套项目 CRKB（公司研究知识底座）已基于 Cognee 产品化**（Docker 部署落地、API 契约 v1.0 冻结）：TA-CN 作为消费方经 REST + MCP 接入，公司知识图谱层不自建；v5.0 四库中的公司库由 CRKB 承载
- 完整映射见 [`current-state-and-vision-mapping.md`](current-state-and-vision-mapping.md)
