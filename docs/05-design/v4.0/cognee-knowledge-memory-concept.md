# 智能助手 v4.0 设想：Cognee 知识与记忆架构

## 📋 文档信息

| 项目 | 内容 |
|------|------|
| 版本 | v4.0 Concept |
| 状态 | 设想 / 草案 |
| 日期 | 2026-03-06 |
| 目标 | 将 Cognee 从“已接入的 MCP 能力”升级为 TradingAgents 的知识与长期记忆增强层 |

---

## 1. 背景

当前系统已经具备：

- 滑动窗口会话记忆（短期上下文）
- 结构化用户画像（MongoDB）
- 金融知识 RAG（`FinancialKnowledgeManager`）
- 分析报告 / 持仓 / 复盘 / 投资计划等业务工具
- 通过 MCP 集成的 Cognee 能力

v4.0 的核心设想：**不把 Cognee 视为单纯的外部工具，而是作为“关系知识 + 长期记忆 + 演化跟踪”层来使用。**

---

## 2. 设计目标

### 2.1 希望解决的问题

1. 助手只能记住短期对话，跨会话长期关系记忆不足
2. 报告、持仓、交易、复盘、投资计划之间缺少统一的关系层
3. 年报 / 季报 / 公告等文档更容易做原文检索，不容易做“多年变化跟踪”
4. 用户偏好、行为习惯、纪律偏差还缺少长期演化分析能力

### 2.2 v4.0 中 Cognee 的定位

Cognee 不作为以下能力的替代：

- 不替代 MongoDB 的业务真相源
- 不替代现有向量 RAG 的原文检索职责
- 不替代结构化用户画像

Cognee 主要承担以下职责：

1. **长期关系记忆层**：记住用户、股票、主题、报告、计划、复盘之间的长期关联
2. **企业演化知识层**：从年报等文档中提取“变化”而非只存原文
3. **推理增强层**：支持“变化趋势、关系链、前后矛盾、长期模式”类问题

---

## 3. 信息架构分类（建议采用 6+1 模型）

## 3.1 六大核心类别

### A. 投研对象知识

包含：

- 股票、指数、板块、主题
- 公司、行业、宏观、政策、监管
- 年报、季报、公告、新闻、研报、纪要

本质：**系统研究的对象本身**

### B. 系统能力知识

包含：

- 工作流、Agent、工具、提示词、模板、MCP 能力说明

本质：**系统如何工作、如何编排能力**

### C. 用户知识

包含：

- 用户身份、画像、风险偏好、关注行业、股票关注列表、持仓、交易计划、长期兴趣点

本质：**这个用户是谁、偏好什么、如何决策**

### D. 任务与产物知识

包含：

- 分析任务、分析报告、持仓分析、组合分析、交易复盘、投资计划产物、中间结论

本质：**系统运行后的结果资产**

### E. 运行上下文知识

包含：

- 当前会话历史、最近关注股票、当前 session 状态、临时确认状态、工具调用现场上下文

本质：**本次交互现场正在发生什么**

### F. 系统配置知识

包含：

- LLM 配置、模型目录、Provider 配置、MCP Server 配置、调度配置、平台配置

本质：**系统依靠什么被部署和治理**

## 3.2 增强类别：事件知识

建议单独建模一类跨域信息：**事件知识**。

包含：

- 财报发布、政策发布、管理层变动、并购重组、业绩预告、重大合同、产能扩张、用户买卖操作、系统分析触发

本质：**驱动关系变化与状态演化的关键事件**

---

## 4. 存储与检索分工

| 类别 | 真相源 | 主要检索方式 | 是否适合进入 Cognee |
|------|--------|--------------|----------------------|
| 投研对象知识 | 文档库 + MongoDB | RAG + 结构化查询 + 图谱 | 适合，尤其是变化与关系部分 |
| 系统能力知识 | MongoDB 配置/定义 | 精确查询 + 少量语义检索 | 可选，不是重点 |
| 用户知识 | MongoDB | 结构化查询 + 图谱 | 很适合长期关系部分 |
| 任务与产物知识 | MongoDB 报告/任务库 | 精确查询 + 图谱 | 很适合结论演化部分 |
| 运行上下文知识 | 会话存储 | 直接读取 | 不建议全量进入 Cognee |
| 系统配置知识 | 配置中心 / `.env` / MongoDB | 精确查询 | 不建议进入 Cognee |
| 事件知识 | 文档/任务/业务库 | 时间线 + 图谱检索 | 非常适合 |

### 4.1 结论

- **MongoDB**：负责结构化事实、配置、状态和业务权威数据
- **RAG**：负责原文片段、知识段落、文档证据召回
- **Cognee**：负责关系知识、变化跟踪、长期记忆、事件链推理

## 5. Cognee 的两个核心方向

## 5.1 方向一：用户投资记忆图谱

目标：构建“用户—股票—计划—行为—复盘—偏差”的长期关系图。

适合回答：

- 我最近反复关注哪些股票？
- 我对某只股票的看法怎么变了？
- 我最常见的交易问题是什么？
- 我的交易计划和实际执行偏差最大在哪里？

### 建议输入数据

- 用户画像摘要
- 股票关注列表变化
- 持仓变化
- 交易复盘结论
- 投资计划规则
- 对话中识别出的稳定偏好事实

## 5.2 方向二：企业演化知识图谱

目标：构建“公司—年份—战略—风险—财务—事件”的演化图。

适合回答：

- 这家公司近 3~5 年发生了哪些关键变化？
- 哪些风险项在多年报告中反复出现？
- 公司是什么时候开始强调某个战略方向？
- 经营逻辑、收入结构、管理层表述是否发生变化？

### 建议输入数据

- 年报 / 季报提取结果
- 公告摘要
- 研究报告摘要
- 管理层纪要提取
- 重大事件提取

---

## 6. 年报场景的使用原则

Cognee **适合做年报跟踪型知识库**，但不建议把整份原文直接当图谱输入。

### 推荐方式

先做结构化提取，再进入 Cognee：

- 财务指标变化
- 业务结构变化
- 战略表述变化
- 风险项变化
- 管理层变化
- 重大事件变化

### 不推荐方式

- 全量原文直接入图
- 把 Cognee 当作年报原文仓库
- 用图谱替代原始文档检索

### 最佳协作方式

1. 用 RAG 找原文证据
2. 用 Cognee 找变化主线和关系链
3. 由助手生成“有来源、有时间线”的总结

---

## 7. 助手检索策略建议

不是每次用户发问都查询 Cognee，而是**按问题类型路由**。

### 优先查 Cognee 的问题

- 带“之前 / 上次 / 最近几次 / 长期 / 多年 / 变化 / 演化 / 是否一致”这类表达
- 需要串联报告、持仓、复盘、投资计划的关系问题
- 需要总结用户行为模式、纪律偏差、长期兴趣点的问题
- 需要总结企业多年变化、风险延续、战略变化的问题

### 不优先查 Cognee 的问题

- 实时行情查询
- 单次报告详情查询
- 普通金融知识解释
- 当前任务状态查询

---

## 8. 写入策略建议

Cognee 的写入应采用：**事件驱动 + 异步写入 + 提炼后写入**。

### 建议触发写入的事件

- 分析任务完成
- 交易复盘生成
- 投资计划更新
- 用户持仓发生关键变化
- 年报 / 季报 / 公告完成解析
- 对话中识别出稳定偏好或长期事实

### 不建议直接写入的内容

- 高频行情
- 全量聊天原文
- 临时 session 状态
- 无法追溯来源的随意推断

---

## 9. 风险与边界

1. **业务真相源仍然是 MongoDB**，图谱不是主数据库
2. **RAG 仍然负责原文证据检索**，Cognee 不替代文档库
3. **所有图谱知识都应可追溯来源**，带 user_id / symbol / year / source_id / section 等标记
4. **必须严格做用户隔离**，避免多用户记忆串线
5. **避免全量灌入低价值数据**，保持图谱干净、稳定、可解释

---

## 10. 分阶段设想

### Phase 1：关系记忆最小落地

- 用户长期记忆图谱最小版
- 分析报告 / 复盘 / 计划关系写入
- 助手支持“历史观点、长期关注、行为偏差”类查询

### Phase 2：企业演化图谱

- 年报 / 季报 / 公告提取入图
- 支持“企业多年变化、风险延续、战略演化”类问答

### Phase 3：跨图谱综合推理

- 企业演化图谱 + 用户记忆图谱联合检索
- 支持“企业变化是否匹配该用户风格 / 计划 / 风险偏好”类辅助推理

---

## 11. v4.0 概念结论

对于 TradingAgents，Cognee 的最佳定位不是单纯的“知识库”或“外部工具”，而是：

- **用户投资长期记忆图谱**
- **企业长期变化知识图谱**
- **事件与关系推理增强层**

因此，v4.0 可以将知识与记忆架构明确分成：

1. MongoDB：结构化业务真相源
2. RAG：原文与证据召回层
3. Cognee：关系、变化、长期记忆与事件链推理层

这将使智能助手从“能回答、能操作”进一步升级为：**能够持续记住、跟踪变化、理解关系、辅助长期决策的投资助手。**
