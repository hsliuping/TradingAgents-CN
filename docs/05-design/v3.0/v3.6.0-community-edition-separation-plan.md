# v3.6.0 社区版开源分离方案

> 版本：v3.6.0 规划稿
> 主题：社区版（开源）与 Pro 版（闭源）的代码分离
> 状态：规划中
> 依赖输入：[付费功能清单](../../../付费功能清单.md)

## 文档信息

| 项 | 说明 |
|----|------|
| 版本号 | v3.6.0（v3.5 为架构优化版，本版专注开源分离，不叠加功能主题） |
| 核心问题 | 项目要整体开源，但付费功能必须保留闭源——如何用一套代码同时维护「闭源 Pro」和「开源社区版」 |
| 方案性质 | 架构收敛 + 工程管道，不以新功能为主题 |
| 关联决策 | Build in Public 自媒体策略、贡献者引入计划、字节 Seed 共创投稿 |
| 分支决策 | 公开仓 `community` 分支先行（`main` 保持 v1.x，稳定后切换）；私有仓 `v3.6-community` 承载收敛改造并长期保留为社区版基线——改造成果验收后**合并回 `pro-main`**（pro-main 基于该结构改造演进），此后 `pro-main → v3.6-community` 定期单向同步 |

## 现状基线（双仓库拓扑）

本方案不是从零建仓，而是在既有双仓库结构上落地：

| 仓库 | Remote | 性质 | 分支现状 |
|------|--------|------|---------|
| TradingAgents-CN | `origin` | 公开仓（开源） | `main` 停在 v1.x（早期开源版本），长期未同步 |
| TradingAgents-CN-Pro | `pro` | 私有仓（Pro） | `pro-main` 为 v3.x 开发主线；`release/jdyun-v3.0` 为京东云发布分支；`v3.6-community` 为本方案工作分支 |

关键事实：

- 两仓自 v1.x 之后分叉，v2.x～v3.5 的演进全部发生在私有仓，公开仓用户停留在 v1.x；
- 开发/发布的区分在私有仓内部以分支实现（`pro-main` 主线、`release/*` 发布分支）；
- 社区版与 Pro 的区分是**仓库级**（双仓）：社区版代码由私有仓基线经发布管道单向生成，公开仓不承载两个版本的多分支维护。

**分支决策（已确认）**：

1. 公开仓采用 **community 分支先行**：社区版首发推送 `community` 分支并行验证，`main` 暂保持 v1.x 不动，待社区版稳定后再切换；
2. 私有仓 `v3.6-community` **长期保留为社区版基线分支**：先作为工作分支完成收敛改造，验收后**合并回 `pro-main`**——收敛改造成果进入 `pro-main`，`pro-main` 基于该代码结构改造并继续演进；此后 `v3.6-community` 转为社区版发布基线，接收 `pro-main` 定期单向同步。

## 一、背景与动机

1. **单人开发不可持续**：开发、维护、运营、合作四线并行，精力见底。需要通过开源引入社区贡献者，把开发压力转化为社区协作。
2. **License 收入持续衰减**：零售付费被大厂免费模型稀释，闭源保护的恰是收入占比最小且在下滑的部分。
3. **开源的战略收益**：
   - 用户认可的是**这个产品本身**，独立框架仓库没有产品形态，用户不认（已明确否决）；
   - 开源仓库是贡献者漏斗的入口；
   - 是自媒体 Build in Public 的载体（2 万公众号粉丝激活）；
   - 对平台合作（京东云、字节 Seed 共创）是加分项而非障碍。

## 二、目标与非目标

**目标**：
1. 公开 GitHub 仓库发布**社区版**：基础功能完整可用，即用户认识的这个产品（单股研究、AI 助手、筛选、复盘等主链路）。
2. 付费功能在社区版中**不存在**（整体剔除，非"锁定"），已付费用户无退费依据。
3. 私有仓内以 `pro-main`（Pro 主线）与 `v3.6-community`（社区版基线）双分支承载：收敛改造成果合并回 `pro-main`，此后 `pro-main → v3.6-community` 定期单向同步，剥离过程自动化、可重复、可校验。
4. 社区贡献（issue/PR）可回流私有仓，反哺 Pro 版。

**非目标**：
- 不做新功能（本版本只做分离）；
- 不追求社区版用户 100% 功能对齐 Pro（配额、进阶能力差异是刻意设计）；
- 不在本版实现全自动双仓同步（前期人工 cherry-pick 即可）。

## 三、核心约束与原则

| # | 约束 | 原则 |
|---|------|------|
| 1 | 已付费用户购买的功能，绝不能出现在公开代码中 | 边界画在**门控层**（路由/UI/服务），引擎层共享 |
| 2 | 社区版必须"完整可用"而非残废版 | 主链路（登录→配置→分析→报告）在社区版必须闭环 |
| 3 | Pro 版（含付费用户、京东云版）零回归 | 收敛改造只做"搬文件、集中注册"，不改逻辑 |
| 4 | 剥离过程可机器校验 | 泄露扫描 + 启动自检 + 冒烟测试三道防线 |

## 四、架构决策：私有主仓 + 发布管道

### 4.1 方案对比

| 方案 | 做法 | 结论 |
|------|------|------|
| A. 原地分层重构 | core/ 拆 framework/finance 双包，Pro 依赖框架包 | 否决：动几百处 import，付费用户在线，回归风险不可控 |
| B. 独立框架仓库 | 元能力层抽新通用仓库 | **否决（用户明确）**：开源的必须是这个产品本身，用户不认无产品形态的框架 |
| C. **私有主仓 + 剥离发布管道** | 私有仓双分支（`pro-main` 主线 / `v3.6-community` 社区版基线，改造成果回合主线），发布脚本按剔除清单生成公开仓 | **选定**：零重构风险、边界清晰、可自动化 |

### 4.2 选定方案

```
私有仓 TradingAgents-CN-Pro
│
├─ v3.6-community（v3.6 工作分支：收敛改造在此完成）
│    │
│    │  ① 合并回 pro-main：收敛验收通过后，
│    │     收敛结构进入 pro-main（pro-main 换基到新结构）
│    ▼
├─ pro-main（Pro 开发主线 / Pro 事实源，基于收敛后结构演进）
│    │
│    │  ② 定期单向同步：Pro 新功能与共享修复流入社区版基线
│    ▼
├─ v3.6-community（社区版发布基线，长期保留）
│    │
│    │  ③ scripts/publish_community.py（按剔除清单删除 + 替换 stub）
│    ▼
公开仓 TradingAgents-CN
├─ community（社区版发布分支，先行验证）
│    │  稳定后 main 切换指向；此前 main 保持 v1.x 不动
│    │
│  issue / PR（贡献者）
▼
④ 人工 cherry-pick 回私有仓（引擎/共享代码 → pro-main；社区版专属 → v3.6-community）
```

社区版代码 = `v3.6-community` 基线经发布管道剥离后的**子集 + 少量 stub 替换**。分支生命周期：`v3.6-community` 先是 v3.6 工作分支（收敛改造）→ 改造成果**合并回 `pro-main`**（pro-main 换到新结构继续演进）→ 此后转为社区版发布基线，按发布节奏从 `pro-main` 定期同步。Pro 的每次发版按需触发一次社区版发布。

## 五、开源边界：三层模型

代码按"引擎层 / 门控层 / 内容层"划分，前层开源保留、后两层剥离：

### 5.1 引擎层（开源保留）

这些是免费主链路运行所必需，且是社区贡献者的参与面：

- 多智能体分析引擎：`tradingagents/`（上游开源 Apache 2.0）、`core/agents/` 框架部分
- 工作流引擎：`core/workflow/engine.py`、`builder.py`、`validator.py`（**引擎保留，Pro UI/路由剔除**——免费单股分析内部就在用这套引擎）
- Skill 运行时：`core/skills/`（解析/执行/转换）
- LLM 统一客户端：`core/llm/`
- 记忆系统、状态管理、数字溯源与 Schema 校验：`core/memory/`、`core/state/`
- 全部金融数据工具：`core/tools/implementations/`（**开源**，这是用户要的产品核心能力）
- FastAPI 应用骨架、用户认证、系统配置：`app/` 骨架部分

### 5.2 门控层（剥离——社区版中删除）

即 [付费功能清单](../../../付费功能清单.md) 的全部代码载体：

| 类别 | 剥离对象 |
|------|---------|
| 后端 Pro 路由 | `workflows.py`、`scheduled_analysis.py`、`email.py`、`watchlist_groups.py`、`trading_system.py`、`templates_debug.py`、`reports.py`、`advanced_courses.py`（或裁剪）、`tools.py`、`agents.py`、prompt 模板相关路由、数据保存六路由（stock_data / financial_data / historical_data / news_data / social_media） |
| 前端 Pro 页面 | 分析流模块全部 12 个子页面（Skill 中心、Agent 工坊、工作流编辑器、AI 工作流架构师、MCP 等）、模板三件套、Prompt 三件套、渠道推送 |
| 权限门控 | `app/core/permissions.py` 的 `PRO_FEATURES` / `require_pro` / `require_feature` → 社区版 stub |
| License 体系 | `core/licensing/` → 社区版 stub（配额改为内置常量，取 Free 档） |
| Pro 专属服务 | 批量/定时分析服务、导出报告、交易计划检查、Agent 工坊/工作流生成服务 |

### 5.3 内容层（裁剪）

| 内容 | 社区版处理 |
|------|-----------|
| 30 节高级课程 | 只保留前 5 节免费课（`advancedCourses.ts`、`advancedCourseContent.ts`、`docs/07-courses/` 裁剪） |
| 知识星球引流组件 | **保留**（内容付费不属于代码付费功能，且是社区版→付费的自然转化入口） |
| Pro 版宣传/定价文档 | 不进公开仓 |
| 京东云版代码 | 不进公开仓（`JDYUN_MODE` 相关分支保留与否由自检决定，倾向保留——它是环境分支不是付费功能） |

## 六、社区版功能范围（用户视角）

社区版用户实际得到的（= 免费功能全集，刻意不含任何 Pro 项）：

1. 用户注册/登录、系统配置（LLM Provider、数据源 Token）
2. 单股研究（1-3 级深度）、分析任务中心、报告查看
3. AI 智能助手（会话、工具调用、报告问答）
4. 条件筛选、选股助手（免费部分）
5. 模拟交易与操作复盘（基础）
6. 自选股（基础，不含分组）
7. 数据自动同步（分析链路内），手动数据管理入口剔除
8. 学习中心（前 5 节课程）+ 知识星球引流
9. 部署：源码运行 + 社区版 Docker 镜像（可选发布项，见 8.3）

**付费用户沟通口径**（用于 FAQ/回复）：Pro 版卖的是进阶生产力（批量、定时、Agent 工坊、分析流、导出、模板体系）与服务；社区版是产品基础能力，两者边界清晰，Pro 功能在社区版代码中不存在。

## 七、代码收敛改造（前置重构，在 `v3.6-community` 分支完成）

剥离能"整文件删除"的前提是付费代码已收敛到文件级边界。改造在 `v3.6-community` 上完成并验收后，**合并回 `pro-main`**（见 M2），成为 Pro 主线的新结构。当前三类欠账：

### 7.1 后端路由注册集中化

现状：`app/main.py`（及可能的分模块注册点）直接 import 全部 router。
改造：路由注册收敛到 `app/router_registry.py` 单一文件，`PRO_ROUTERS` 与 `COMMUNITY_ROUTERS` 分列。发布脚本处理方式：删除 Pro 路由文件 + 用社区版注册文件替换。
**要求：只搬注册行，不动路由实现。**

### 7.2 前端 Pro 页面目录化

现状：`frontend/src/router/index.ts` 单文件混合全部路由（含 `requiresPro: true` 的 17 个页面）；Pro 页面散在 views 目录。
改造：
1. Pro 页面组件统一迁入 `frontend/src/views/pro/`（按现有模块名建子目录）；
2. Pro 路由定义集中到 `router/pro.routes.ts` 并在 `index.ts` 展开；
3. 菜单/导航入口中的 Pro 项集中到独立配置（`navigation.pro.ts`）。
发布脚本：删除 `views/pro/`、`pro.routes.ts`、`navigation.pro.ts`，`index.ts` 展开处替换为空数组。

### 7.3 权限门控 stub 化

现状：`require_pro` / `check_feature` 散布于路由依赖与引擎调用点，`core/licensing/` 还承载 Tier 配额（分析师数、工作流数、并发数等）。
改造：
1. 私有仓内把"门控检查"统一收敛到 `app/core/permissions.py` 与 `core/licensing/` 的既有入口（已有基础，补漏即可）；
2. 新增 `core/licensing/community_stub.py`：提供同签名的无门控实现 + 内置社区版配额（分析师 4、研究员 2、单并发、API 限额同 Free 档）；
3. 发布脚本将门控入口指向 stub（或直接替换 import）。

### 7.4 课程内容裁剪

`advancedCourses.ts` / `advancedCourseContent.ts` 增加免费/付费数据分离（按 `FREE_LESSON_COUNT=5` 过滤已存在，确认数据文件物理可分）；`docs/07-courses/v3.0/` 发布时仅保留前 5 节。

### 7.5 收敛验收

每项收敛以"发布脚本不碰共享文件内部"为验收标准：剔除动作必须是**文件级删除/整文件替换**，不允许 sed 式行级修改共享文件。

## 八、发布管道设计

### 8.1 `scripts/publish_community.py` 主流程

```
1. 校验私有仓工作区干净、当前为 `v3.6-community` 分支的可发布 commit（已同步 `pro-main` 至目标基线）
2. 复制工作树 → 临时目录（不污染私有仓）
3. 按 docs/community-edition/removal-manifest.yaml 执行剔除：
   a. 删除 Pro 路由文件 / views/pro / pro.routes / navigation.pro
   b. 替换 router_registry.py / index.ts 注册入口为社区版
   c. 替换 licensing → community_stub
   d. 裁剪课程内容文件与 docs/07-courses
   e. 替换 README / 定价文档 / CLA / CONTRIBUTING / LICENSE（社区版专属）
4. 泄露扫描（见 8.2）
5. 社区版启动自检 + 冒烟测试
6. 初始化 git 历史策略 → 推送公开仓 `community` 分支（`main` 保持 v1.x 不动，稳定后切换）
7. 输出发布报告（剔除统计、扫描结果、冒烟结果）
```

剔除清单用 YAML manifest 维护（文件路径 + 替换规则），新增付费功能时同步登记——**新 Pro 功能不入 manifest = 发布即泄露**，纳入发版检查清单。

### 8.2 三道校验防线

| 防线 | 手段 | 拦截目标 |
|------|------|---------|
| 泄露扫描 | grep 扫描产物中的付费标识符：`PRO_FEATURES`、`require_pro`、`tier_features`、付费路由路径（`/api/workflows` 等 30+ 项模式库） | 付费代码/标识残留 |
| 启动自检 | `docker build` 社区版 Dockerfile + 容器内 `import app.main`、依赖导入全通过 | 剔除导致的断链 |
| 冒烟测试 | 容器起服务 → 登录 → 配置 Mock LLM → 跑一次 1 级单股分析 → 校验报告生成 | 主链路闭环可用 |

### 8.3 发布节奏与产物

- **节奏**：随 Pro 版发版同步触发（低频、高质量），不追每次 commit；
- **产物**：公开仓源码（主产物）；社区版 Docker 镜像为可选项（发布到开源版 Docker Hub 账号，tag 用 `community` / 具体版本号，不用 `latest`）；
- **公开仓分支模型**：`community` 分支先行承载社区版发布；`main` 保持 v1.x，待社区版连续稳定（建议 ≥2 个版本、冒烟全通过）后切换指向 `community`；贡献 PR 在公开仓 review，cherry-pick 回私有仓；
- **community 分支历史策略**：基于 `main`（v1.x）创建后以全量提交接入社区版代码，保留演进脉络；若单次 diff 过大影响审查，可改为 orphan 新历史，切换 `main` 时将 v1.x 归档为 `legacy-v1.x` 分支；
- **版本衔接口径**：公开仓 README 与首次发布说明需说明——v2.x～v3.5 为 Pro 闭源演进期，社区版自 v3.6.0 起与 Pro 同源开源、版本号对齐，并附 v1.x 老用户的升级/迁移说明（配置与数据兼容性以实际验证为准）。

## 九、社区贡献回流机制

```
公开仓 issue/PR → 分类：
  a. 共享代码（引擎/免费功能/文档）→ cherry-pick 回私有仓 pro-main → 定期合并流入 v3.6-community → 随下次发布回流公开仓
  b. 纯社区版问题 → 公开仓直接修（注意：社区仓没有历史，改动以 patch 形式带回 v3.6-community）
  c. 涉及 Pro 边界 → 关闭并引导至付费渠道
```

- 前期人工 cherry-pick，量级可控（预期贡献者少）；
- 回流纪律：**`pro-main` 是 Pro 事实源，`v3.6-community` 是社区版基线事实源**，公开仓不承载独立演进；两分支同步方向：收敛改造经一次性合并进入 `pro-main`，此后 `pro-main → v3.6-community` 定期单向同步（基线上除社区适配外不做独立演进）；
- `good first issue` 标签随首次发布准备 5-10 个（文档、测试、示例方向为主）。

## 十、License / CLA / 商标

| 项 | 决策 |
|----|------|
| 开源许可证 | Apache 2.0（与上游 `tradingagents/` 一致，无传染风险） |
| CLA | 启用（如 cla-assistant.io），保住对贡献代码的商业使用权，否则未来无法收回商业版 |
| 商标 | README 声明：项目名与商标归作者；Pro 版、京东云版为商业发行渠道 |
| 合规 | 公开仓 README 保留"研究辅助工具、不构成投资建议"声明（与产品口径一致） |

## 十一、实施计划（里程碑）

## 十二、风险与对策

| 风险 | 等级 | 对策 |
|------|------|------|
| 剔除遗漏导致付费代码泄露 | 高 | manifest 全量登记 + 三道防线 + 发布前人工抽查；新 Pro 功能纳入发版 checklist |
| 剔除过度导致社区版不可用 | 中 | 冒烟覆盖主链路；引擎层"最小保留集"以免费链路实际 import 关系为准（自检脚本可输出依赖证据） |
| Pro 版回归（收敛改造/合并回引入） | 中 | 收敛只搬不改；M1、M2 验收均跑全量回归 |
| 付费用户不满/要求退费 | 中 | 边界原则（Pro 功能在社区版"不存在"而非"锁住"）；统一沟通口径提前公告 |
| 双仓/双分支漂移 | 中 | 收敛成果一次性合并回 `pro-main`（M2）统一结构；此后 `pro-main → v3.6-community` 单向定期同步；公开仓不承载独立演进；每次同步合并后跑社区版冒烟 |
| 双分支结构差异引发合并冲突 | 中 | M2 合并回后双分支结构同源，冲突面收敛到注册点；收敛以新增文件为主（`router_registry.py`、`views/pro/`、`pro.routes.ts`、`navigation.pro.ts`）；解冲突原则：注册一律走集中文件 |
| 社区版维护负担反噬精力 | 中 | 低频发布节奏；issue 分流规则（§九）明确"Pro 边界问题即关闭" |
| 证券合规 | 低 | 免责声明保留；社区版不含任何交易指令类输出（既有合规改造成果天然继承） |

## 十三、验收标准

1. **泄露零命中**：发布产物通过泄露扫描（付费标识符模式库 0 命中），人工抽查确认。
2. **社区版闭环**：全新环境 clone 公开仓 → 按 README 部署 → 登录 → 完成一次单股分析并查看报告。
3. **Pro 零回归**：v3.6.0 Pro 版发版后付费功能全量验收通过（沿用 v3.x acceptance-test-plan 体系，补 v3.6.0 验收计划）。
4. **可重复发布**：任意两次执行 publish_community.py 产物一致（幂等）；发布耗时在分钟级。
5. **贡献可回流**：公开仓提交的共享代码改动可干净 cherry-pick 回私有仓（引擎类 → `pro-main`、社区版专属 → `v3.6-community`，各演练一次验证）。
6. **合并回与同步可执行**：`v3.6-community` 干净合并回 `pro-main`（M2，无残留冲突、Pro 回归通过）；此后 `pro-main → v3.6-community` 定期合并流程完整跑通一次，冲突解决规则（注册走集中文件）有效。
