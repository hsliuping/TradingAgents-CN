# TradingAgents-CN v3.1.0 验收测试计划

## 文档目的

本计划用于 `v3.1.0` 小版本验收。

该版本聚焦“跟踪闭环”，目标是让用户从一次性使用转向持续复访。

## 版本定位

- 版本主题：跟踪闭环版
- 目标用户：高频使用者、老用户
- 发布形态：GA
- 核心目标：让用户形成“跟踪 -> 提醒 -> 复盘 -> 计划”的闭环

## 纳入范围

1. 定时分析。
2. 统一通知中心。
3. QQ Gateway 与 IM 推送。
4. 持仓分析。
5. 交易复盘。
6. 投资计划。

## 不纳入范围

1. MCP Server。
2. QMT 和 ETF。
3. AI 工作流架构师、Agent 工坊、Skill 自动生成。
4. 回测服务。

## 验收重点

1. 跟踪对象是否能按计划持续触发分析。
2. 分析完成后是否能通过站内与 QQ 渠道稳定触达。
3. 持仓、复盘、投资计划是否能形成真实的复访理由。

## 核心验收场景

### 场景 A：定时分析调度

1. 创建一条定时分析。
2. 暂停该配置。
3. 重新启用该配置。

预期结果：

1. 配置能成功创建。
2. 状态切换正确。
3. 后续任务触发节奏符合配置预期。

### 场景 B：统一通知触达

1. 触发一项分析任务。
2. 检查站内通知。
3. 检查 QQ 侧消息推送。

预期结果：

1. 通知中心能看到对应事件。
2. QQ 渠道能收到与任务一致的推送。
3. 站内与外部通知内容不冲突。

### 场景 C：QQ 会话接入

1. 通过 QQ 渠道发起多轮对话。
2. 切换不同 session 来源。
3. 验证身份绑定后查询个人相关数据。

预期结果：

1. Session 隔离正确。
2. 用户映射正确。
3. 不会跨用户读取持仓、计划或复盘信息。

### 场景 D：持仓分析

1. 列出持仓。
2. 查看指定持仓的分析详情。

预期结果：

1. 列表可读、可筛选。
2. 详情内容足够支撑继续观察或决策准备。

### 场景 E：交易复盘与投资计划

1. 查看复盘列表与详情。
2. 查询当前投资计划。

预期结果：

1. 复盘与计划可作为后续跟踪依据，而不是孤立页面。
2. 用户能理解这些页面与助手、通知之间的关系。

## 入口条件

1. 调度器、通知、QQ Gateway 在测试环境可用。
2. 持仓、复盘、投资计划有可验证的测试数据。
3. 已准备至少一个完整的 QQ 绑定测试账号。

## 退出条件

1. 定时分析、站内通知、QQ 推送全链路通过。
2. 持仓、复盘、投资计划页面不存在阻塞级空数据或错用户问题。
3. 关键留存闭环可被测试人员连续走通，不依赖手工修数据。

## 风险提示

1. 调度、通知、IM 是跨模块链路，局部看似可用不代表整体可发布。
2. 如果 QQ 身份映射和通知一致性不稳，会直接影响用户信任感。

## 文档使用方式

本文件分成两层：

1. 上半部分保留版本级验收目标、范围和退出条件。
2. 下半部分给出可直接执行的详细验收计划和测试用例。

建议测试人员不要跳着测，而是按“环境基线 -> QQ 单账号映射稳定性 -> 定时分析 -> 通知触达 -> 持仓/复盘/计划 -> 闭环回归”的顺序执行。

## 测试目标拆解

本次验收不是单模块功能确认，而是确认以下三件事是否同时成立：

1. 用户可以配置跟踪对象，并按计划持续触发分析。
2. 分析结果可以稳定通过站内与 QQ 触达给正确的人。
3. 持仓、复盘、交易计划三块内容能支撑用户继续复访，而不是孤立页面。

### 当前轮次环境限制

1. 当前环境为单机版，仅有 1 个已绑定 QQ 测试账号。
2. 本轮不执行多 QQ 账号绑定对比、未绑定 QQ 账号拒绝策略、多账号 QQ 映射隔离实测。
3. 场景 C 在本轮改为验证：单账号绑定正确、单账号多轮会话连续、单账号重新进入会话后映射仍稳定。
4. 如后续具备多账号环境，再回补跨账号 QQ 隔离用例。

## 测试优先级与放行规则

- `P0`：阻塞发布。失败则本版本不应按 GA 放行。
- `P1`：高优先级问题。允许带已知问题清单放行，但必须有明确规避方案。
- `P2`：体验优化项。不阻塞放行，但要进入后续版本修复池。

放行建议：

1. 所有 `P0` 用例必须通过。
2. `P1` 用例允许少量已知问题，但不能影响主链路闭环。
3. 在当前单账号环境下，不允许出现身份丢失、通知串任务、QQ 映射漂移、持仓/计划/复盘对象错位这类问题；多账号串号需在后续多账号环境补测。

## 测试环境与测试数据准备

### 环境要求

1. 后端、前端、MongoDB、Redis、worker、scheduler 全部已启动。
2. QQ Gateway 已接入测试环境，可查看 webhook 日志和回调结果。
3. 测试环境可访问站内通知 WebSocket，浏览器端能正常建立连接。
4. 邮件不是本次主验收阻塞项；如邮件链路未配置，可只记录结果，不作为阻塞结论。

### 建议测试账号编排

| --- | --- | --- |

| QQ-A | 唯一已绑定 QQ 测试账号 | 用于单聊、群聊、通知接收 |

1. 用户 A 自选股：4 支。
2. 用户 A 持仓：至少 1 支真实持仓、1 支模拟持仓，便于验证筛选与详情。
3. 用户 A 复盘：至少 1 条交易复盘、1 条阶段复盘，或能够现场创建。
4. 用户 A 交易计划：至少 1 个激活计划，并在复盘中能看到计划关联字段更佳。
5. 如果本地可准备第二个系统用户，可额外补测跨用户隔离；否则本轮标记为 `N/A-环境不具备`。

## 缺陷分级建议

### 阻塞级

1. 无法创建、暂停、启用定时分析。
2. 定时任务根本不触发或明显错过配置时间。
3. 通知发给错误用户或 QQ 推送串号。
4. 持仓、复盘、交易计划出现跨用户读取。
5. 关键页面空白、报错、无法进入。

### 高优先级

1. 站内通知和 QQ 通知内容明显冲突。
2. 单账号会话切换后偶发丢失上下文或读取错误对象。
3. 复盘详情或交易计划详情虽可打开，但关键字段缺失严重。

### 中低优先级

1. 文案不统一。
2. 时间显示不够友好。
3. 通知样式、排序、交互小问题。

## 详细验收用例

### TC-ENV-01 环境与入口基线检查

- 优先级：`P0`
- 目标：确认测试环境满足执行条件，避免后续把环境问题误判成产品问题。
- 前置条件：测试环境已部署完成。

- 操作步骤：

1. 登录 Web 前端，确认系统可进入首页。
2. 打开设置页，确认可进入“定时分析配置”页面 `/settings/scheduled-analysis`。
3. 打开“持仓分析”页面 `/portfolio`。
4. 打开“操作复盘”页面 `/review`。
5. 打开“交易计划”页面 `/trading-system`。
6. 用一个已登录会话保持页面打开 1 至 2 分钟，确认没有连续报错或反复掉线。

- 预期结果：

1. 以上页面均可进入。
2. 前端无阻塞级白屏或 500 报错。
3. 若页面依赖 WebSocket，应能正常连接或至少无持续错误弹窗。

- 建议证据：

1. 各页面入口截图。
2. 浏览器控制台无严重错误截图。

### TC-C-01 QQ 单账号绑定与映射校验

- 优先级：`P0`
- 目标：验证唯一 QQ 测试账号与系统用户的绑定关系正确。
- 前置条件：已准备用户 A 和已绑定的 QQ-A。

- 操作步骤：

1. 使用 QQ-A 与系统机器人发起单聊。
2. 发送“查看我的持仓”。
3. 再发送“查看我的交易计划”或“查看我的复盘”。
4. 记录返回内容中的个人数据是否均对应用户 A。

- 预期结果：

1. QQ-A 返回的数据始终对应用户 A。
2. 同一账号连续查询持仓、计划、复盘时，身份映射不漂移。
3. 不会出现返回空白用户、默认用户或其它错误身份的数据。

- 建议证据：

1. QQ-A 会话截图。
2. 后端 gateway 日志中 user mapping 片段。

### TC-C-02 单账号会话连续性与来源切换一致性

- 优先级：`P0`
- 目标：验证单账号在多轮对话中身份稳定；如有群聊场景，再补充验证来源切换一致性。
- 前置条件：QQ-A 已绑定；若有群聊环境可额外验证群聊 @ 机器人。

- 操作步骤：

1. 在 QQ-A 单聊中连续发送 3 至 5 轮消息，例如“查看我的持仓”“查看我的交易计划”“查看我的复盘”。
2. 观察连续多轮回复是否都保持同一用户身份和上下文。
3. 如果群聊环境可用，再在群聊 @ 机器人发送一次相同查询。
4. 对比单聊和群聊返回的身份口径是否一致。

- 预期结果：

1. 单账号多轮会话中，身份映射保持稳定。
2. 若验证了群聊与单聊，两个来源的身份口径应一致。
3. 不会出现同一账号前后两轮拿到不同用户或错误对象数据的情况。

- 建议证据：

1. 单聊连续多轮截图。
2. 如有群聊，再补 1 张群聊截图或 session 日志。

### TC-C-03 单账号重新进入会话后映射稳定

- 优先级：`P0`
- 目标：验证同一 QQ 账号在重新进入会话、间隔一段时间后，仍能稳定映射回同一用户。
- 前置条件：QQ-A 已绑定且至少完成过一次成功查询。

- 操作步骤：

1. 使用 QQ-A 完成一次成功查询后，关闭当前聊天窗口或等待一段时间再重新发起会话。
2. 重新发送“查看我的持仓”。
3. 再发送“查看我的交易计划”或“查看我的复盘”。

- 预期结果：

1. 重新进入会话后仍能正确识别为用户 A。
2. 不需要重复绑定或人工修复上下文。
3. 不会因为重新进入会话而丢失身份、返回空白数据或错误对象。

- 建议证据：

1. 重新进入前后的 QQ-A 会话截图。
2. 如可见，重新识别 user mapping 的日志。

### TC-A-01 创建定时分析配置

- 优先级：`P0`
- 目标：验证用户能创建一条可执行的定时分析配置。
- 前置条件：用户 A 已登录且至少有 1 个可选分组或可分析自选股。

- 操作步骤：

1. 进入“定时分析配置”页面 `/settings/scheduled-analysis`。
2. 新建配置，名称建议使用“v3.1 验收测试-1”。
3. 添加至少 1 个启用的时间段，建议设置为未来 5 至 10 分钟内便于观察触发。
4. 配置默认分析深度、分组或股票范围。
5. 打开“完成后通知”相关选项。
6. 保存配置。

- 预期结果：

1. 配置创建成功，列表中可见新配置。
2. 配置信息回显正确，包括名称、启用状态、时间段。
3. 不出现重复名称、时间段缺失、保存失败但前端提示成功等问题。

- 可选后台核对：

1. 检查是否成功创建对应配置记录。
2. 检查调度器是否注册对应任务。

- 建议证据：

1. 创建成功截图。
2. 配置详情截图。

### TC-A-02 暂停与重新启用定时分析配置

- 优先级：`P0`
- 目标：验证配置启停切换正确。
- 前置条件：TC-A-01 已通过。

- 操作步骤：

1. 在配置列表中禁用刚创建的配置。
2. 刷新页面，确认状态仍为禁用。
3. 重新启用该配置。
4. 再次刷新页面。

- 预期结果：

1. 禁用后状态立刻切换为禁用。
2. 启用后状态立刻切换为启用。
3. 状态持久化正确，不会刷新后丢失。
4. 禁用和启用都不会误创建多条重复调度任务。

- 建议证据：

1. 禁用前后、启用前后截图。
2. 如可见，调度日志片段。

### TC-A-03 定时分析按计划触发

- 优先级：`P0`
- 目标：验证“配置存在”不只是静态状态，而是真的能按时间执行。
- 前置条件：TC-A-01、TC-A-02 已通过；时间段设置为近期可观察。

- 操作步骤：

1. 保持配置为启用状态。
2. 等待触发时间到达。
3. 观察页面任务状态、后端日志或任务中心是否出现新的定时分析任务。
4. 记录任务开始时间与配置时间的偏差。
5. 如支持“测试执行”按钮，可再执行一次人工触发，确认与定时触发结果口径一致。

- 预期结果：

1. 到达配置时间后有新任务被触发。
2. 任务归属用户正确，范围正确。
3. 执行频率与配置一致，不会漏触发或重复多次触发。
4. 失败时有可理解日志，而不是静默失败。

- 建议证据：

1. 任务开始时间截图或日志。
2. 对应任务 ID。

### TC-B-01 分析完成后生成站内通知

- 优先级：`P0`
- 目标：验证分析结果能进入站内通知链路。
- 前置条件：已有一条已触发或人工触发的分析任务。

- 操作步骤：

1. 使用用户 A 保持登录状态。
2. 等待定时分析任务完成。
3. 观察顶部通知入口、通知抽屉或未读数变化。
4. 打开通知列表，查看是否出现与本次任务对应的通知。

- 预期结果：

1. 通知能成功生成。
2. 标题、内容、时间、链接或来源信息基本完整。
3. 通知归属用户正确，不会出现在其他用户会话中。

- 建议证据：

1. 通知出现截图。
2. 未读数变化截图。

### TC-B-02 通知未读数、列表、已读状态一致

- 优先级：`P1`
- 目标：验证通知中心基础交互正确。
- 前置条件：至少已有 1 条未读通知。

- 操作步骤：

1. 记录当前未读数。
2. 打开通知列表，确认新通知在列表中。
3. 将其中 1 条通知标记已读。
4. 再执行“全部已读”。
5. 刷新页面重新进入。

- 预期结果：

1. 未读数与列表中的未读项数量一致。
2. 单条已读后未读数减少。
3. 全部已读后未读数归零。
4. 刷新页面后已读状态保持一致。

- 建议证据：

1. 已读前后截图。
2. 刷新后的结果截图。

### TC-B-03 QQ 推送内容与站内通知一致

- 优先级：`P0`
- 目标：验证外部触达与站内通知语义一致。
- 前置条件：唯一已绑定 QQ 测试账号可接收消息，且定时分析任务已完成。

- 操作步骤：

1. 等待站内通知出现。
2. 同时查看该 QQ 会话中是否收到对应推送。
3. 对比两边的标题、任务归属、摘要信息、时间表达是否一致。
4. 如有链接或任务标识，检查是否能对应到同一任务。

- 预期结果：

1. QQ 推送与站内通知针对同一事件。
2. 两边不应一个说成功、一个说失败。
3. 两边不应出现不同用户、不同股票范围、不同任务摘要。

- 建议证据：

1. 站内通知截图。
2. QQ 推送截图。
3. 同一任务 ID 或时间戳对照记录。

### TC-D-01 持仓列表展示与筛选

- 优先级：`P0`
- 目标：验证持仓页面具备基本可用性。
- 前置条件：用户 A 至少存在真实持仓和模拟持仓。

- 操作步骤：

1. 打开“持仓分析”页面 `/portfolio`。
2. 查看默认列表是否成功加载。
3. 分别切换数据来源筛选，例如真实持仓、模拟持仓、全部。
4. 如页面支持历史持仓或统计信息，同步检查页面是否能正常展示。

- 预期结果：

1. 列表可正常加载。
2. 筛选后结果数量与来源口径一致。
3. 不出现明显字段错位、空白字段泛滥、数据来源混乱。

- 建议证据：

1. 全部、真实、模拟三种视图截图。

### TC-D-02 指定持仓分析详情可读

- 优先级：`P0`
- 目标：验证单个持仓详情不是空壳页面。
- 前置条件：用户 A 至少有 1 条可分析持仓。

1. 在持仓列表中选择一条持仓，打开详情或分析弹窗。

1. 详情页或弹窗能打开。
2. 内容足够支撑“继续观察”或“后续复盘准备”，而不是只有空标题和占位文案。
3. 若暂无分析结果，也应给出清晰提示，而不是直接报错。

- 建议证据：

1. 详情截图。
2. 若有历史分析记录，补一张历史记录截图。

### TC-D-03 持仓数据跨用户隔离

- 优先级：`P0`
- 目标：验证持仓不会跨用户展示。
- 前置条件：用户 A、用户 B 都存在持仓数据。

- 操作步骤：

1. 登录用户 A，记录持仓列表中的关键股票代码。
2. 退出并登录用户 B，查看持仓列表。
3. 对比两边是否只显示各自数据。
4. 若支持持仓详情，分别打开同名入口验证详情归属是否仍正确。

- 预期结果：

1. 用户 A 看不到用户 B 的持仓。
2. 用户 B 看不到用户 A 的持仓。
3. 切换用户后，不会短暂闪现上一用户数据。

- 建议证据：

1. 两个账号的持仓列表截图。
2. 如发现闪现或缓存串号，录屏更好。

### TC-E-02 当前交易计划查询与状态确认

- 优先级：`P0`
- 目标：验证交易计划不是“有页面没内容”。
- 前置条件：用户 A 至少有 1 个交易计划，最好有 1 个激活计划。

- 操作步骤：

1. 打开“交易计划”页面 `/trading-system`。
2. 查看列表页是否有计划。
3. 打开其中 1 个计划详情。
4. 确认计划的状态、版本、核心规则、激活状态是否可见。
5. 如有激活计划入口，验证当前激活计划是否与预期一致。

- 预期结果：

1. 计划列表和详情可打开。
2. 激活状态清晰，不会出现多个互相冲突的“当前计划”。
3. 用户能明确知道当前后续跟踪是依据哪一个计划。

- 建议证据：

1. 列表页截图。
2. 计划详情截图。

### TC-E-03 复盘与计划可作为后续跟踪依据

- 优先级：`P1`
- 目标：验证复盘、计划与后续行为之间存在认知闭环。
- 前置条件：用户 A 至少有 1 条复盘和 1 个计划。

- 操作步骤：

1. 查看一条复盘详情，确认是否能看到与交易计划相关的字段、名称或规则上下文。
2. 打开当前交易计划，核对其核心规则是否能帮助理解复盘结论。
3. 用自然语言总结：如果用户明天再次回来，是否能知道“接下来应该关注什么”。

- 预期结果：

1. 复盘不是孤立文本。
2. 计划不是孤立配置页。
3. 两者至少能共同构成一个可复访的跟踪依据。

- 建议证据：

1. 复盘详情中关联计划字段截图。
2. 计划详情中核心规则截图。

### TC-LOOP-01 跟踪闭环端到端回归

- 优先级：`P0`
- 目标：按版本主题验证“跟踪 -> 提醒 -> 复盘 -> 计划”的完整闭环。
- 前置条件：前述 P0 用例大部分已通过。

- 操作步骤：

1. 用户 A 创建或启用一条近期可触发的定时分析配置。
2. 等待任务触发并完成。
3. 在站内确认收到通知。
4. 在唯一已绑定 QQ 测试账号中确认收到一致的推送。
5. 回到 Web 端打开持仓分析页面，查看本次跟踪对象的持仓或相关分析。
6. 打开对应复盘页面，确认可以基于当前结果继续复盘。
7. 打开交易计划页面，确认用户能找到当前应遵循的计划。
8. 用一句话回答：“如果我是老用户，我会不会因为这条链路明天再回来？”

- 预期结果：

1. 从触发到触达全链路打通。
2. 用户能在同一套产品中找到后续观察、复盘和计划依据。
3. 闭环过程不依赖手工改库或临时补数据。

- 放行判定：

1. 若本用例失败，通常说明版本主题尚未真正成立，即使各单页功能存在，也不建议按“跟踪闭环版”验收通过。

- 建议证据：

1. 定时分析配置截图。
2. 站内通知截图。
3. QQ 推送截图。
4. 持仓、复盘、交易计划页面截图各 1 张。
