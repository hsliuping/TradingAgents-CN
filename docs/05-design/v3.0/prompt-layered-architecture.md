# TradingAgents-CN v3.0 — 分层提示词架构设计方案

> **2026-06-21 落地说明**: 原设计中的五层动态组装（基础模板→场景策略→行业画像→个股画像→能力块→任务块）过于复杂。实际落地采用简化方案——仅保留行业画像注入：Agent 执行时根据股票所属行业，从 `industry_analysis_profiles` 查询行业配置，格式化为分析维度追加到提示词末尾。37 个行业大类配置已入库，运行时注入已接入 `base.py`。详见 [行业分析框架速查手册](../reference/industry-analysis-framework.md)。

## 1. 背景与问题定义

### 1.1 当前基础能力

当前系统已经具备以下能力：

- `prompt_templates` 支持 `Node > Workflow > Agent 默认` 三层优先级
- 运行时通过 `core/agents/base.py` → `tradingagents/utils/template_client.py` 加载有效模板
- 模板内容已结构化为 `system_prompt`、`tool_guidance`、`analysis_requirements`、`output_format`、`constraints`
- 行业/个股画像已形成独立模型与集合：
  - `industry_analysis_profiles`
  - `stock_analysis_profiles`
- 行业画像生成流程已升级为聊天式协作，并支持能力覆盖评估

### 1.2 当前问题

尽管现有模板系统已支持按 Agent / Workflow / Node 精细覆盖，但模板内容本身仍偏向**单体式 Agent 模板**，在以下场景下出现明显限制：

1. **行业分析与个股分析共用一套正文，业务语义混杂**
2. **行业画像、个股画像、能力边界与角色定义耦合过深**
3. **模板作者需要手动维护大量业务占位符，维护成本高**
4. **无法自然表达“行业默认 + 个股覆盖”的继承关系**
5. **系统能力透明度不足，模型和用户都不清楚哪些数据可直接获得、哪些依赖 MCP / Skill / 外部导入**

### 1.3 本方案要解决什么

本方案不是替换现有三层优先级模型，而是在其内部补上一层**内容组装架构**：

> 先决定“取哪份模板”，再决定“这份模板内部如何被行业、个股、能力、任务上下文组装”。

---

## 2. 设计目标

### 2.1 核心目标

1. **角色模板与业务画像解耦**：基础角色提示词只描述 Agent 职责，不直接写死行业/个股业务细节
2. **行业/个股分层注入**：行业画像作为默认框架，个股画像作为覆盖层
3. **能力边界显式注入**：将内置数据、MCP、Skill、外部导入缺口明确传递给模型与用户
4. **兼容现有模板结构**：优先复用 `prompt_templates.content` 五段式结构，不推翻现有渲染链路
5. **支持产品演进**：既可支撑当前配置页，也可支撑后续聊天式 Prompt 设计助手

### 2.2 非目标

以下内容不属于本方案直接范围：

- 不重新设计 `prompt_templates` 的基础 CRUD API
- 不替换当前 `template_client.py` 的整体优先级逻辑
- 不在本阶段引入完整 DSL / Jinja 模板引擎重构
- 不把所有 Prompt 维护改造成模块拖拽式编辑器

---

## 3. 总体方案

### 3.1 核心思想

将最终 Prompt 拆分为五类语义层：

1. **基础角色模板层**（Base Role Template）
2. **场景注入策略层**（Scenario Injection Policy）
3. **业务画像层**（Industry / Stock Profile）
4. **能力说明层**（Capability Block）
5. **任务指令层**（Task Block）

最终运行时组装公式：

```text
Final Prompt = Base Role Template
             + Scenario Injection
             + Analysis Context Block
             + Capability Block
             + Task Block
```

其中：

- `Analysis Context Block` 为后端统一生成的结构化上下文块
- `Capability Block` 为后端统一生成的能力边界说明
- `Task Block` 为用户当前问题、工作流节点任务或本轮分析目标

### 3.2 分层职责划分

| 层 | 职责 | 是否与 Agent 强绑定 |
|----|------|--------------------|
| 基础角色模板层 | 定义角色、目标、输出风格、约束 | 是 |
| 场景注入策略层 | 定义行业/个股/能力块如何注入 | 是 |
| 业务画像层 | 描述行业重点、个股特殊项、可比公司、关键指标 | 否 |
| 能力说明层 | 描述数据可得性、外部依赖、缺口 | 否 |
| 任务指令层 | 描述当前分析任务、用户要求、节点职责 | 否 |

### 3.3 与旧模式的差异

| 旧模式 | 新模式 |
|--------|--------|
| 每个 Agent 手动维护整份行业/个股版本模板 | Agent 只维护基础模板，业务内容由上下文块注入 |
| 行业维度、个股维度直接散落在正文里 | 由画像服务统一生成结构化块 |
| 只能表达“同一 Agent 不同模板” | 能表达“同一 Agent + 不同场景 + 不同画像 + 不同能力边界” |
| 用户看不到数据边界 | 能力块与覆盖评估共同提供透明说明 |

## 4. 五层架构定义

### 4.1 基础角色模板层

该层由当前 Prompt 模板管理页面中的 Agent 卡片负责维护。

职责包括：

- 角色身份与立场
- 分析目标与工作边界
- 输出风格与结构
- 风险提示与合规约束

明确要求：

- 不在该层直接硬编码某个行业或某只股票的专属指标
- 不在该层堆叠大量与行业/个股绑定的业务知识
- 不在该层直接描述“哪些数据拿不到”，能力边界交由能力块表达

### 4.2 场景注入策略层

该层控制同一个 Agent 在不同分析场景中如何消费上下文。

建议至少支持以下场景：

- `general`：通用分析
- `industry`：行业分析
- `stock`：个股分析

该层不直接承载长文本，而承载注入策略，例如：

- 是否启用行业画像注入
- 是否启用个股画像注入
- 个股分析时是否继承行业画像
- 注入强度：`none / summary / full`
- 是否附带能力边界说明
- 是否附带外部依赖提醒
- 注入位置：`system_prompt / analysis_requirements / constraints`

### 4.3 业务画像层

业务画像层由现有配置体系承载：

- 行业画像：`industry_analysis_profiles`
- 个股画像：`stock_analysis_profiles`

该层负责提供：

- 核心分析维度
- 关键指标
- 分析重点说明
- 可比公司
- 个股特殊说明

设计原则：

1. **行业画像是默认框架**
2. **个股画像是覆盖层，不是平级重复定义**
3. **画像内容由服务层合并，不由前端或模板作者手工拼接**

### 4.4 能力说明层

能力说明层的作用有两个：

1. 告诉用户当前草案哪些内容可以落地
2. 告诉模型哪些内容可以直接下结论、哪些必须保守表达

能力说明至少区分三类：

- **可直接使用**：系统内置数据源可支持
- **可间接获取**：依赖 MCP / Skill / 推理衍生
- **当前缺失**：需要用户提供外部数据或手动导入

该层必须与覆盖评估结果保持一致，避免 UI 与 Prompt 描述互相矛盾。

### 4.5 任务指令层

任务指令层描述当前一次分析要完成什么。

来源可以是：

- 用户当前输入
- 工作流节点任务说明
- 对话式修订要求
- 系统自动生成的分析目标摘要

该层是高频变化层，不应固化到基础模板中。

## 5. 运行时组装规则

### 5.1 行业分析 Prompt 组装

适用场景：目标对象是行业，而非具体股票。

组装顺序建议：

1. 基础角色模板
2. 行业场景注入策略
3. 能力说明块
4. 行业画像块
5. 当前任务块

目标效果：

- 模型先知道“自己是谁”
- 再知道“现在要做行业分析”
- 再知道“哪些数据能拿到、哪些不能”
- 最后拿到行业重点维度和当前任务

### 5.2 个股分析 Prompt 组装

适用场景：目标对象是具体股票。

组装顺序建议：

1. 基础角色模板
2. 个股场景注入策略
3. 能力说明块
4. 行业画像摘要块
5. 个股画像块
6. 当前任务块

关键原则：

> **个股优先，行业兜底。**

也就是先给模型行业共性分析框架，再给个股特殊关注点，最终由合并后的上下文块约束其分析重点。

### 5.3 与现有模板五段式结构的兼容策略

为保证兼容当前 `prompt_templates.content` 结构，v3.0 采用“少量稳定插槽 + 服务层预组装”的模式。

建议对模板作者暴露的稳定变量仅保留：

- `{analysis_context_block}`
- `{capability_block}`
- `{task_block}`

推荐映射方式：

| 现有字段 | 推荐承载内容 |
|----------|--------------|
| `system_prompt` | 基础角色定义 + 总体原则 |
| `tool_guidance` | 工具 / MCP / Skill 使用原则 |
| `analysis_requirements` | `analysis_context_block` + `task_block` |
| `output_format` | 输出结构要求 |
| `constraints` | `capability_block` + 风险/保守表达约束 |

不鼓励模板作者直接拼接诸如 `{industry_dimensions}`、`{stock_dimensions}`、`{external_dependency_notice}` 等细碎业务变量。

## 6. 行业与个股的继承/合并规则

### 6.1 合并原则

当目标为个股时，服务层应先加载行业画像，再应用个股覆盖。

### 6.2 推荐规则

| 规则类型 | 说明 |
|----------|------|
| `inherit` | 默认继承行业画像中的分析维度和关键指标 |
| `append` | 个股可追加专属维度 |
| `override` | 个股可重写某个行业维度的说明或重要性 |
| `disable` | 个股可显式关闭某些行业默认维度 |
| `summary` | 注入给模型的是合并后摘要，而不是两份原始配置并排堆叠 |

### 6.3 合并结果要求

最终注入模型的内容应是一份**已完成归并的分析上下文**，而非：

- 一份行业列表 + 一份个股列表 + 让模型自己猜如何合并

服务层应输出：

- 最终有效维度
- 每个维度的来源（行业 / 个股 / 共同）
- 是否存在外部依赖
- 当前建议保留或弱化的分析项

## 7. 配置与数据模型扩展建议

### 7.1 复用现有集合

本方案直接复用：

- `prompt_templates`
- `industry_analysis_profiles`
- `stock_analysis_profiles`

### 7.2 新增配置概念：`prompt_injection_policies`

建议新增独立集合或等价配置模型，管理“不同 Agent 在不同场景下如何注入上下文”。

建议字段：

| 字段 | 说明 |
|------|------|
| `agent_type` | Agent 类型 |
| `agent_name` | Agent 名称 |
| `scope` | `general / industry / stock` |
| `enabled` | 是否启用 |
| `injection_mode` | `none / summary / full` |
| `inherit_industry_for_stock` | 个股是否继承行业画像 |
| `include_capability_block` | 是否附带能力说明 |
| `include_external_gap_notice` | 是否附带外部依赖提醒 |
| `include_comparable_companies` | 是否注入可比公司 |
| `inject_position` | 推荐注入字段位置 |
| `version` | 版本号 |

说明：

- 该集合表达的是“策略”，不是“大段正文模板”
- 该集合与 `prompt_templates` 互补，不替代 `prompt_templates`

## 8. 产品与界面设计建议

### 8.1 Prompt 管理页改造原则

Prompt 模板管理页面不再只承担“编辑整份模板正文”的职责，而应拆为三类能力入口：

1. **基础模板管理**
2. **场景注入策略管理**
3. **最终 Prompt 实时预览**

### 8.2 推荐页面结构

单个 Agent 的详情页建议拆为 4 个 Tab：

1. **基础角色模板**
2. **行业分析注入策略**
3. **个股分析注入策略**
4. **实时预览**

### 8.3 与画像工作台的关系

行业/个股画像本身继续由独立工作台维护：

- 行业画像：聊天式协作生成与修订
- 个股画像：后续延续同样的多轮对话式流程

Prompt 管理页只负责定义“这些画像如何被不同 Agent 使用”，不负责重新编辑画像本身。

### 8.4 预览能力要求

实时预览页至少支持选择：

- Agent
- 分析场景（行业 / 个股）
- 行业名称
- 股票代码
- 是否附带能力块

并显示：

- 最终 Prompt
- 各段来源说明
- 使用了哪些画像与策略
- 当前能力缺口提醒

## 9. 分阶段落地路径

### Phase 1：兼容式落地（优先）

目标：最小改动接入分层架构。

实施内容：

- 保留现有 `prompt_templates` 五段式结构
- 新增 `analysis_context_block` / `capability_block` / `task_block` 三个稳定变量契约
- 新增服务层组装逻辑，统一合并行业/个股/能力块
- Prompt 页面新增“实时预览”能力

### Phase 2：策略配置化

目标：把注入规则从硬编码迁移到数据库策略。

实施内容：

- 新增 `prompt_injection_policies`
- 支持按 Agent + 场景配置注入强度、注入位置、是否继承行业画像
- 支持不同 Agent 看到不同粒度的画像摘要

### Phase 3：聊天式 Prompt 设计助手

目标：让用户通过自然语言优化 Prompt，而非手动改正文。

实施内容：

- 用户通过对话提出 Prompt 修改意图
- 系统自动建议策略变更或基础模板变更
- 支持最终 Prompt 对比预览与确认保存

## 10. 与 v3.0 三层配置模型的关系

### 10.1 不冲突，属于不同维度

现有三层配置模型解决的是：

> **当前请求应该选中哪一份模板 / 哪一份绑定配置。**

本方案解决的是：

> **选中模板之后，这份模板内部如何组装成更贴近行业/个股场景的最终 Prompt。**

### 10.2 组合后的完整逻辑

可抽象为两步：

1. **配置选择层**：按 `Node > Workflow > Agent 默认` 选出模板与注入策略
2. **内容组装层**：按“基础模板 + 场景策略 + 画像块 + 能力块 + 任务块”生成最终 Prompt

这意味着：

- 三层配置模型继续保留
- 本方案作为三层配置模型内部的内容标准化规范
- 后续 Prompt 优化、工作流专属 Prompt 生成、聊天式 Prompt 助手都应遵循本规范

## 11. 风险与约束

### 11.1 主要风险

1. **Prompt 过长**：行业画像、个股画像、能力说明同时注入可能导致上下文膨胀
2. **能力描述不一致**：UI 覆盖评估与 Prompt 能力块必须来自同一来源
3. **策略过度复杂**：如果对模板作者暴露过多插槽和开关，会再次回到高维护成本

### 11.2 控制原则

- 优先摘要注入，而不是原始配置全文灌入
- 优先由服务层合并，而不是由模板作者手工拼装
- 优先保持少量稳定变量契约，而不是开放大量碎片化占位符

---

## 12. 结论

本方案确认：TradingAgents-CN Pro 在 v3.0 阶段的 Prompt 架构应从“单体式 Agent 模板”升级为“分层式 Prompt 组装架构”。

最终设计结论如下：

1. **基础模板只定义角色，不承载过多业务画像**
2. **行业画像作为默认框架，个股画像作为覆盖层**
3. **能力说明块必须成为正式 Prompt 组成部分**
4. **模板作者只面对少量稳定插槽，不直接维护大量业务字段**
5. **Prompt 管理页应围绕“基础模板 + 注入策略 + 预览”重构**
6. **本方案作为 v3.0 Prompt 相关设计的正式留档，供后续实现与演进参考**
