# TradingAgents-CN v2.1.0 vs v3.0 产品能力详细对比

> 文档用途：为 v3.0.0-beta.4 测试版本发布提供产品侧说明，帮助用户、运营和市场团队快速理解两代版本的核心差异与升级价值。
> 版本：v3.0.0-beta.4 | 更新日期：2026-07-08

---

## 一、版本定位与产品哲学对比

### 1.1 核心目标演进

| 维度 | v2.1.0 | v3.0 |
|------|--------|------|
| **核心目标** | 把投资研究全流程「串起来」 | 让 AI 从局部辅助走向全流程协同 |
| **用户交互方式** | 表单/配置驱动的模块操作 | 自然语言对话 + Agent 主动规划 |
| **扩展方式** | 内置工具 + 固定模板 | Skill 工坊 + Agent 工坊 + MCP 生态 |
| **技术底座** | FastAPI + Vue + MongoDB/Redis + LangChain | 在 v2.x 基础上增加 LangGraph 工作流、能力索引、版本化工具管理 |
| **面向用户** | 有明确分析需求的进阶用户 | 普通投资者也能通过对话完成复杂任务 |

### 1.2 产品哲学差异

**v2.1.0 的产品假设**：
- 用户知道自己想要什么分析
- 用户愿意学习各个模块的功能边界
- 系统提供能力，用户按需组合

**v3.0 的产品假设**：
- 用户更习惯用自然语言表达投资问题
- 用户不关心功能边界，只关心结果
- 系统应该主动理解意图、规划任务、调用工具、呈现结论

### 1.3 一句话总结

> **v2.1.0 是「功能齐全的投资研究工作台」，v3.0 是「听得懂话、会自己动手的 AI 投资助手」。**

## 二、智能助手：从分析入口到统一协同入口

### 2.1 功能对比

| 能力 | v2.1.0 | v3.0 |
|------|--------|------|
| 单次问答/触发分析 | ✅ 基础问答、单股分析触发 | ✅ 保留并增强，支持更自然的对话 |
| 多轮任务协同 | ❌ 各模块独立，需用户手动切换 | ✅ 助手可跨模块推进任务 |
| 个股/批量分析发起 | ✅ 通过页面操作 | ✅ 自然语言+页面双入口 |
| 历史报告查询 | ✅ 报告列表查询 | ✅ 助手可直接回答「最近怎么看某只股票」 |
| 定时分析任务管理 | ✅ 页面配置 CRON | ✅ 助手可查询/创建/管理 |
| 自选股/持仓/复盘/计划查询 | ✅ 各模块分别查看 | ✅ 助手统一入口 |
| 解读热点事件 | ⚠️ 需手动触发分析 | ✅ 可直接询问助手 |
| 复杂任务拆解 | ❌ 无 | ✅ 助手自动拆解为多步骤执行 |

### 2.2 典型对话差异

**v2.1.0 用户路径**：
```
打开个股分析 → 输入 600519 → 选择分析师 → 等待 3 分钟 → 查看报告
```

**v3.0 用户路径**：
```
用户：帮我看看贵州茅台最近的财务风险
助手：好的，我来调用财报分析师和风险分析师为您分析...
       [自动完成] → 输出结构化风险报告
```

### 2.3 产品价值

v3.0 让智能助手从「分析触发器」升级为「投资研究协同入口」，核心解决三个问题：

1. **降低学习成本**：用户不需要记住每个模块在哪里
2. **减少切换成本**：复杂任务由助手自动串联多个模块
3. **提升连续性**：同一对话上下文内完成从选股到复盘的完整链路

## 三、Agent 工坊：从固定分析师到自定义分析专家

### 3.1 模块定位

| 维度 | v2.1.0 | v3.0 |
|------|--------|------|
| 是否存在 | ❌ 不存在 | ✅ 新增核心模块 |
| 创建方式 | 只能使用内置分析师 | 对话式创建完整 Agent |
| 定制深度 | 浅（模板参数调整） | 深（职责、输出、工具、提示词全定制） |
| 测试验证 | ⚠️ 无系统化测试 | ✅ 真数据测试 + LLM 评估 |
| 版本管理 | ❌ 无 | ✅ draft/testing/active 多状态 + 版本回滚 |

### 3.2 Agent 工坊完整流程

v3.0 的 Agent 工坊把创建 Agent 的过程标准化为 7 个阶段：

```
① 需求探索 → ② 需求确认 → ③ 能力盘点 → ④ 方案选择
    ↓
⑤ 按方案实现 → ⑥ 真数据测试 → ⑦ 发布/迭代
```

#### 阶段 1：需求探索（Exploring）
- **作用**：Nanobot 作为产品专家，多轮询问用户目标、维度、输出格式、样本股票
- **v2.1.0 对应**：无，用户需自行决定需要什么分析
- **v3.0 改进**：通过对话澄清模糊需求，避免生成错 Agent

#### 阶段 2：需求确认（Requirement Confirmation）
- **作用**：输出需求确认稿，明确 Agent 做什么、输出什么、不做什么
- **关键设计**：确认稿不包含工具候选，用户不需要知道系统有哪些工具
- **v3.0 价值**：避免「我以为系统能做这个，结果做不出来」的期望错位

#### 阶段 3：能力盘点（Capability Check）
- **作用**：系统内部扫描现有工具/Skill，运行真实 gap 分析
- **技术实现**：
  - `search_project_capabilities`：向量搜索 + 覆盖率评分
  - `analyze_agent_workshop_gaps`：LLM 深度分析 blocking/non-blocking gaps
- **v2.1.0 对应**：无，用户不知道系统能力边界

#### 阶段 4：方案选择（Plan Selection）
- **作用**：基于 gap 结果给出 2-4 个候选方案
- **典型方案**：
  - **A. 完整方案**：补齐所有缺口，输出完整功能
  - **B. 快速方案**：用现有工具做简化版
  - **C. 调整方案**：缩小需求范围到现有能力可覆盖的子集
- **v3.0 价值**：让用户在可行性、成本、功能完整度之间做知情选择

#### 阶段 5：按方案实现（Implementation）
- **Plan A**：创建 Agent → 补齐 blocking gaps → 构建版本
- **Plan B**：创建 Agent → 跳过 blocking gaps → 直接构建简化版
- **Plan C**：回到需求探索，重新缩小范围

#### 阶段 6：真数据测试（Testing）
- **作用**：用真实股票代码测试 Agent 效果
- **评估维度**：工具调用覆盖率、输出格式正确性、推理质量、数据可追溯性
- **v2.1.0 对应**：无，内置分析师无法测试

#### 阶段 7：发布/迭代（Publishing/Iterating）
- **发布**：版本变为 active，可参与正式分析流程
- **迭代**：根据测试 evidence 选择补能力、调 Prompt 或重跑测试

### 3.3 Agent 工坊输出物

创建成功的 Agent 包含：

| 输出物 | 说明 |
|--------|------|
| AgentSpec | Agent 规格：名称、职责、输出字段、约束 |
| Prompt 模板 | 系统提示词 + 用户提示词 |
| Runtime Config | 调用模型、温度、工具白名单 |
| Version | draft/testing/active 多状态版本 |
| Gap Report | 能力缺口分析与解决方案记录 |

### 3.4 产品价值

1. ** democratize Agent 创建**：非开发者也能创建专属分析师
2. **避免能力错配**：需求确认 + 能力盘点 + 方案选择三重保障
3. **保证输出质量**：真数据测试 + LLM 评估，不合格不发布
4. **可追溯可迭代**：Agent → Gap → Skill → Test → Publish 全链路记录

## 四、Skill 工坊：从零散工具到可演进的工具生态

### 4.1 模块定位

| 维度 | v2.1.0 | v3.0 |
|------|--------|------|
| 是否存在 | ✅ 已支持基础版本 | ✅ 重大升级 |
| 创建方式 | AI 根据需求生成代码 | AI 根据需求生成代码 + 多轮验收 |
| 迭代升级 | ⚠️ 生成全新 Skill，无版本关系 | ✅ 完整版本链 |
| 版本显示 | ❌ 无 | ✅ 所有版本并行展示 |
| 旧版本保护 | ❌ 升级可能覆盖旧版 | ✅ 迭代不覆盖，已绑定 Agent 的旧 Skill 继续可用 |
| 任务管理 | ⚠️ 全部显示，占用空间 | ✅ 默认隐藏已完成，支持删除 |
| 字段名防幻觉 | ❌ 无 | ✅ 源头注入 + 验收器兜底 |
| 沙箱污染防护 | ⚠️ 基础 | ✅ 禁止 `if __name__ == "__main__":` 块 |

### 4.2 Skill 生成管线

v3.0 的 Skill 工坊包含完整的生成管线：

```
需求分析 → 侦察探测 → 代码生成 → 静态验证 → 沙箱执行
    → 业务验收 → 质量评估 → 边缘测试 → 保存/迭代
```

#### 4.2.1 需求分析（Requirement Analyzer）
- **作用**：把用户需求转化为结构化的 SkillSpec
- **v3.0 关键增强**：
  - 从 helper docstring 提取真实字段名，注入 spec 生成提示词
  - 防止 LLM 幻觉出不存在的字段名（如 `no_pledge_note` vs `pledge_status_note`）
  - 迭代模式下注入 `_v{N}` 命名约束

#### 4.2.2 侦察探测（Reconnaissance）
- **作用**：探测 helper 函数的真实返回结构、字段名、数据样例
- **关键规则**：必须使用有数据的股票进行探针检测（如 000002 万科）
- **v3.0 价值**：确保代码生成器能看到完整的返回结构，而不是猜测字段名

#### 4.2.3 代码生成（Code Generator）
- **作用**：根据 spec 和侦察结果生成 Python 函数代码
- **v3.0 关键增强**：
  - 系统提示词中明确禁止 `if __name__ == "__main__":` 调试块
  - 要求使用 pipeline_tool 进行工具调用
  - 优先使用 helper 函数，禁止自行实现等价数据获取或处理逻辑
  - 强调 helper 透传铁律：调用 helper → `.get()` 取字段 → 组装输出

#### 4.2.4 验收评估（Business Verifier）
- **作用**：验证 Skill 输出是否符合业务预期
- **v3.0 关键修复**：
  - 当 spec 已有 `required_field` 检查时，跳过 fact_report 中的冲突检查
  - 避免 spec 和验收规则互相矛盾导致的无限迭代

#### 4.2.5 迭代控制（Iteration Controller）
- **作用**：根据验收结果决定继续迭代还是结束
- **v3.0 增强**：支持最多 10 轮迭代，每轮生成独立的代码快照

### 4.3 版本管理 V3 方案

这是 v3.0 相比 v2.1.0 最重要的改进之一。

#### 4.3.1 v2.1.0 的问题
- 迭代生成的 Skill 与原 Skill 名字完全不同
- 用户不知道哪个是新版
- 旧 Skill 可能被覆盖，导致已绑定 Agent 出错

#### 4.3.2 v3.0 的解决方案
- **独立文档**：每次迭代创建新的 MongoDB 文档
- **`_v{N}` 后缀**：如 `stock_pledge_trend_risk` → `stock_pledge_trend_risk_v2` → `stock_pledge_trend_risk_v3`
- **`parent_skill_id` 版本链**：记录根 Skill 的 tool_id
- **并行显示**：所有版本在列表中同时展示，视觉分组体现系列关系
- **旧版保护**：已绑定 Agent 的旧 Skill 不会被覆盖或删除

#### 4.3.3 版本链数据结构

```json
{
  "tool_id": "stock_pledge_trend_risk_v3",
  "parent_skill_id": "stock_pledge_trend_risk",
  "version": 3,
  "version_note": "修复空数据分支的 message 字段",
  "display_name": "股权质押趋势风险_v3",
  "is_active": true
}
```

### 4.4 Skill 绑定与执行

| 能力 | v2.1.0 | v3.0 |
|------|--------|------|
| 绑定到 Agent | ✅ 基础绑定 | ✅ 批量绑定、解绑 |
| 执行日志查询 | ⚠️ 部分 | ✅ 完整日志列表 + 统计 |
| SkillHub 导入 | ❌ 无 | ✅ 可导入腾讯 SkillHub 工具 |
| 任务状态展示 | ⚠️ 仅展示进行中 | ✅ 展示失败/进行中/已完成，支持从失败恢复 |

### 4.5 产品价值

1. **工具能力可演进**：Skill 可以持续迭代，而不是每次重新发明
2. **版本关系清晰**：用户一眼看出哪些 Skill 是同一系列的不同版本
3. **系统稳定性**：旧版本继续服务已绑定 Agent，避免升级导致故障
4. **质量有保障**：多轮验收 + 字段名防幻觉 + 沙箱污染修复

## 五、MCP 生态：从封闭系统到开放扩展平台

### 5.1 模块定位

| 维度 | v2.1.0 | v3.0 |
|------|--------|------|
| MCP 服务器管理 | ❌ 无 | ✅ 创建/发现/启用/禁用 |
| MCP 工具接入 Agent | ❌ 无 | ✅ Agent 可调用 MCP 工具 |
| MCP 凭证加密存储 | ❌ 无 | ✅ Fernet 加密 + 列表页遮蔽 |
| 启动自动恢复 | ❌ 无 | ✅ 重启后自动恢复 MCP 工具注册 |
| 工具调用日志 | ❌ 无 | ✅ 记录到 tool_execution_logs |

### 5.2 MCP 接入流程

```
添加 MCP 服务器 → 发现工具 → 启用服务器 → Agent 调用 MCP 工具
```

### 5.3 典型应用场景

- **接入 QMT 数据源**：从量化交易软件获取实时行情和交易信号
- **接入专业金融 API**：如 Wind、同花顺 iFinD 等
- **接入自定义分析工具**：用户自研的因子计算、风险评估工具

### 5.4 产品价值

v3.0 让 TradingAgents-CN 从「自带工具的封闭系统」变成「可接入外部工具的开放平台」，大幅扩展了系统的数据边界和能力边界。

## 六、股票分析工作流：从单点分析到智能协同

### 6.1 功能对比

| 能力 | v2.1.0 | v3.0 |
|------|--------|------|
| 单股分析 | ✅ A股/港股/美股/ETF | ✅ 保留并增强 |
| 批量分析 | ✅ 并发控制 | ✅ 保留 |
| 定时分析 | ✅ CRON 任务 | ✅ 保留 |
| 动态 Agent 字段聚合 | ⚠️ 基础 | ✅ `analyst_reports` 等聚合变量更完善 |
| 工坊 Agent 参与分析 | ❌ 无 | ✅ 自定义 Agent 可进入正式分析流程 |
| 工具调用摘要 | ⚠️ 部分 | ✅ 完整记录 `tool_call_summaries` |
| 报告导出 | ✅ PDF/Markdown | ✅ 保留 |
| 多 Agent 辩论 | ✅ 看涨/看跌研究员 | ✅ 保留并增强 |
| 报告期口径修复 | ⚠️ 部分 | ✅ 季报营收/净利年化后再算周转指标 |

### 6.2 报告期口径修复

这是一个容易被忽视但非常重要的改进。

**v2.1.0 的问题**：
- 季报的营收、净利直接用于计算 DSO、存货周转等指标
- 季报是季度数据，年报是年度数据，口径混用导致指标失真

**v3.0 的修复**：
- 季报的营收、净利先年化（乘以 4）
- 再用年化后的数据计算 DSO、存货周转等指标
- 确保不同报告期的指标口径一致

### 6.3 动态字段聚合

**v2.1.0**：报告结构相对固定，扩展 Agent 需要改动模板
**v3.0**：
- 引入 `analyst_reports` 等聚合变量
- 工坊 Agent 的输出自动进入聚合
- 最终报告的 `structured_reports` 包含动态 Agent 字段

### 6.4 产品价值

1. **分析能力可扩展**：用户创建的 Agent 能立即参与正式分析
2. **指标更准确**：报告期口径修复避免错误结论
3. **结果更透明**：工具调用摘要让分析过程可追溯

## 七、持仓分析与交易复盘：从结果展示到闭环管理

### 7.1 功能对比

| 能力 | v2.1.0 | v3.0 |
|------|--------|------|
| 持仓管理 | ✅ 添加/查看/盈亏 | ✅ 保留 |
| 持仓分析 | ✅ 技术面/基本面/风险/建议 | ✅ 保留并支持动态字段注入 |
| 交易复盘 | ✅ 基础复盘报告 | ✅ 保留并支持工作流模式 |
| 复盘案例库 | ⚠️ 基础 | ✅ 可查询历史复盘案例 |
| 复盘与计划联动 | ⚠️ 弱 | ✅ 增强联动 |

### 7.2 交易复盘工作流

v3.0 支持两种复盘模式：

1. **标准模式**：直接生成复盘报告
2. **工作流模式**：使用多 Agent 工作流进行深度复盘

复盘报告包含：
- **timing**：买卖时机评估
- **position**：仓位管理评估
- **emotion**：情绪控制评估
- **attribution**：收益归因分析
- **summary**：总结与改进建议

### 7.3 产品价值

1. **形成投资闭环**：选股 → 分析 → 交易 → 持仓 → 复盘 → 改进
2. **案例可沉淀**：历史复盘案例进入案例库，供后续参考
3. **问题可追溯**：复盘报告帮助用户识别反复出现的错误模式

## 八、提示词与模板系统：从静态配置到动态治理

### 8.1 功能对比

| 能力 | v2.1.0 | v3.0 |
|------|--------|------|
| 提示词模板管理 | ✅ 基础管理 | ✅ 增强：版本历史、归档 |
| 提示词注入策略 | ⚠️ 部分模块可用，但路由漏注册 | ✅ 完整模块 |
| 提示词预览 | ⚠️ 路由 404 | ✅ 正常可用 |
| 提示词设计 | ⚠️ 路由 404 | ✅ 正常可用 |
| 分析画像（行业/个股） | ⚠️ 路由 404 | ✅ 独立 analysis_profiles 路由 |
| 模板迁移 | ❌ 无 | ✅ 动态报告模板自动迁移 |

### 8.2 v3.0 修复的路由问题

v2.1.0 中存在 4 个路由漏注册问题，导致相关页面返回 404：

| 路由模块 | v2.1.0 | v3.0 |

## 十、技术/工程架构对比

### 10.1 核心技术栈

| 维度 | v2.1.0 | v3.0 |
|------|--------|------|
| 工作流引擎 | 基础流程控制 | LangGraph 状态机工作流 |
| Agent 状态持久化 | 基础 | LangGraph checkpoint |
| 能力索引 | ❌ 无 | ✅ Qdrant 向量搜索 + 覆盖率评分 |
| 工具元数据标签 | ⚠️ 基础 | ✅ `data_source_handling` 标签 |
| 字段名防幻觉 | ❌ 无 | ✅ 从 helper docstring 提取真实字段名注入 spec |
| 沙箱执行污染防护 | ⚠️ 基础 | ✅ 禁止 `if __name__ == "__main__":` 块 |
| 版本隔离 | ✅ 独立目录/端口/数据卷 | ✅ 保留（v3.0 用 27019/6381/8002/8082） |
| 代码生成 LLM max_tokens | ⚠️ 可能截断 | ✅ 固定 12288 |

### 10.2 LangGraph 工作流

v3.0 引入 LangGraph 作为 Agent 和 Skill 工坊的工作流引擎，核心优势：

1. **状态机驱动**：每个阶段有明确的 state 和 transition
2. **持久化检查点**：中断后可恢复，不丢失进度
3. **条件边清晰**：节点只负责状态修改，边负责决策
4. **人机协同**：`await_user=True` 的节点自动暂停等待用户输入

### 10.3 能力索引

v3.0 新增能力索引服务，用于 Agent/Skill 工坊的能力盘点：

1. **向量搜索**：从 Qdrant 召回 top 16 相关工具
2. **覆盖率评分**：基于工具名称、描述、参数做精确匹配
3. **无阈值过滤**：所有候选都参与排名，不错过潜在可用工具

### 10.4 工程规范增强

v3.0 强化了多项工程规范：

1. **helper 透传铁律**：禁止使用自行实现的分组聚合/趋势计算/字段映射推导
2. **字段名约束**：代码生成必须严格按 helper 的 Returns 说明使用字段
3. **native Koa**：前端代理必须使用 native Koa，避免 ctx 泄漏
4. **数据库版本隔离**：v3.0 必须连接 27019/6381，避免版本 mismatch

## 十二、典型使用场景详细对比

### 场景 1：普通用户想分析一只股票

**v2.1.0 路径**：
1. 进入「个股分析」页面
2. 输入股票代码（如 600519）
3. 选择要调用的分析师（基本面/技术面/新闻/情绪）
4. 点击「开始分析」
5. 等待 2-5 分钟
6. 进入「报告中心」查看结果

**v3.0 路径**：
1. 打开智能助手
2. 输入「帮我分析一下贵州茅台最近的财务风险」
3. 助手自动识别意图 → 规划任务 → 调用相关 Agent
4. 等待 2-5 分钟
5. 助手直接返回结构化风险报告

**差异价值**：v3.0 把 6 步变成 2 步，且不需要用户知道「财务风险」对应哪个模块。

---

### 场景 2：用户想创建一个自定义分析师

**v2.1.0**：
- 无法做到，只能使用系统内置的 4 个分析师
- 如果需要新分析维度，必须等待官方开发

**v3.0**：
1. 进入 Agent 工坊
2. 告诉 Nanobot「我要一个能识别财报风险信号的助手」
3. Nanobot 多轮确认需求边界
4. 系统自动做能力盘点，给出 2-3 个方案
5. 用户选择方案 A（完整版）
6. 系统自动生成 Agent，必要时创建 Skill 补齐缺口
7. 用真实股票测试 Agent 效果
8. 测试通过后发布

**差异价值**：v3.0 让非开发者也能创建专属分析 Agent，并把自定义 Agent 纳入正式分析流程。

---

### 场景 3：用户发现系统缺少某个数据工具

**v2.1.0**：
- 在 Skill 工坊描述需求
- AI 生成代码
- 但迭代升级会生成全新的、无版本关联的 Skill
- 旧 Skill 如果被覆盖，可能导致已绑定 Agent 出错

**v3.0**：
1. 在 Skill 工坊描述需求
2. AI 生成代码并经过多轮验收
3. 需要迭代时，系统生成 `_v2`、`_v3` 等版本
4. 所有版本并行显示，用户知道哪个是最新版
5. 已绑定 Agent 的旧版本继续可用

**差异价值**：v3.0 解决了 Skill 迭代「不知道哪个是新版」和「升级破坏旧 Agent」的问题。

---

### 场景 4：用户想接入外部数据源

**v2.1.0**：
- 需要自行开发适配器
- 需要修改系统代码
- 需要了解 ToolRegistry 的内部机制

**v3.0**：
1. 进入 MCP 管理页面
2. 添加 MCP 服务器（如 QMT、Wind）
3. 点击「发现工具」，系统自动列出可用工具
4. 启用服务器
5. Agent 即可调用 MCP 工具

**差异价值**：v3.0 把外部数据源接入从「开发任务」变成「配置任务」。

---

### 场景 5：用户想管理定时分析任务

**v2.1.0**：
1. 进入定时任务页面
2. 配置 CRON 表达式
3. 选择分析标的和分析师
4. 保存任务

**v3.0**：
1. 对助手说「每周一开盘前帮我分析一下自选股」
2. 助手确认标的和时间
3. 自动创建定时任务

**差异价值**：v3.0 用自然语言替代了复杂的 CRON 配置。

## 十三、升级建议

### 13.1 适合升级到 v3.0 的用户

- 希望用自然语言完成复杂投资研究任务
- 需要自定义 Agent 或扩展系统工具能力
- 有接入外部数据源/MCP 的需求
- 希望 Skill 迭代不破坏已有 Agent 绑定
- 愿意尝试新功能，对测试版本有容忍度

### 13.2 建议保留 v2.1.x 的用户

- 当前工作流已稳定，不需要新功能
- 团队/个人更习惯表单化操作
- 对测试版本稳定性有顾虑
- 主要用于生产环境，不愿承担测试版本风险

### 13.3 版本并存策略

v3.0 使用独立端口和数据卷，与 v2.1.0 完全隔离：

| 版本 | MongoDB | Redis | Backend | 前端 |
|------|---------|-------|---------|------|
| v3.0 | 27019 | 6381 | 8002 | 8082 |
| v2.1.0 | 27018 | 6380 | 8001 | 8081 |
| v2.0.1 | 27017 | 6379 | 8000 | 8080 |

用户可以在同一台机器上同时运行多个版本，互不干扰。
