## 1. 背景

在 v3.0 阶段，系统已经具备了一种很重要的能力雏形：

- 当能力不够时，系统可以发现缺口
- 系统可以报告缺什么能力
- 后续可以由主人审核，决定是否新增 Skill

这说明 TradingAgents 并不是完全静态的系统。

但当进入 v4.0，系统如果要进一步增强：

- 自定义 Agent 团队
- 长期记忆
- 用户私有研究资产
- 分析、计划、执行、复盘闭环

就会更频繁地遇到一个问题：

**当系统发现当前能力不够时，应该如何演进，而又不滑向无监督自主生长？**

因此，v4.0 需要收敛出一个更清晰的答案：

**能力可以继续增长，但必须是受控增长；系统可以发现缺口，但不能未经审核自主扩张。**

---

## 2. 核心定位

### 2.1 什么是受控 Skill 增长

受控 Skill 增长，是指系统具备以下能力：

1. 识别当前任务或长期使用中出现的能力缺口
2. 报告缺口带来的影响
3. 形成候选 Skill 或能力升级建议
4. 将最终决策权交给主人、管理员或系统治理者
5. 审核通过后，再将新能力纳入正式体系

它不是：

- 模型自己决定长什么能力
- 系统自己写入并启用新 Skill
- 无版本、无审计、无责任边界的自动进化

### 2.2 它在 v4.0 中的位置

如果说“长期投研陪伴工作台”是产品目标，“自定义 Agent 团队”是能力组织层，那么“受控 Skill 增长”就是演进机制层。

它负责回答的是：

- 团队能力不够时怎么办
- 哪些能力值得补
- 新能力怎么进入正式体系
- 谁来批准这种升级

---

## 3. 为什么必须坚持“受控”

### 3.1 投研场景天然需要主权和责任边界

TradingAgents 不是通用娱乐型 Agent 系统，而是面向投研和决策辅助的系统。

这意味着：

- 能力扩展会影响分析结果
- 能力扩展会影响用户研究过程
- 能力扩展可能影响长期资产沉淀方式

如果系统可以无监督自主扩张，就会直接破坏：

- 可解释性
- 可审计性
- 用户主权
- 系统边界稳定性

### 3.2 自动增长容易把系统带向平台失控

如果把“发现缺口”直接等同于“自动长 Skill”，很容易出现：

- 系统能力边界越来越松
- 质量参差不齐
- 角色权限越来越混乱
- 用户越来越难理解系统到底会什么、不会什么

从产品角度看，这会把 TradingAgents 拉向一个不必要的方向：

- 自动造系统
- 自动长能力
- 失去可信边界的 AI 平台

这与 v4.0 的工作台型产品收敛方向是冲突的。

### 3.3 审核机制本身就是产品价值的一部分

审核不是效率损耗，而是这个产品可信度的一部分。

它帮助系统回答：

- 这个能力是谁批准进入的
- 为什么需要它
- 适用于哪些角色或任务
- 是否经过验证
- 是否可以回退

这比“系统自己长了一个新能力”更值得信任。

## 4. 哪些情况应触发能力缺口发现

### 4.1 当前任务无法完成

例如：

- 没有合适的工具可调用
- 缺少某类结构化提取能力
- 缺少某类投研规则支持
- 当前团队没有能承担该职责的角色

### 4.2 当前任务能完成，但质量明显不足

例如：

- 某类分析总是缺一块关键维度
- 某类输出总是不稳定
- 某类资料只能原文检索，无法结构化承接

### 4.3 某类需求重复出现

如果同一种能力缺口反复出现，就不应继续靠人工临时补救，而应进入正式的升级评估。

### 4.4 新的工作台能力需要新支撑

例如：

- 新增复盘沉淀场景
- 新增周期整理场景
- 新增用户研究资产导入场景

这些可能要求系统补充新 Skill，但补充方式仍应受控。

## 5. 建议的受控增长流程

### 5.1 第一步：发现缺口

系统识别出：

- 当前任务缺什么能力
- 缺口影响了哪个阶段
- 是工具缺失、规则缺失、角色缺失还是流程缺失

### 5.2 第二步：形成缺口报告

报告至少应包括：

- 缺口名称
- 触发场景
- 影响范围
- 如果不补会造成什么后果
- 建议的补充方向

### 5.3 第三步：生成候选升级项

候选升级项可以是：

- 新 Skill
- 现有 Skill 增强
- 新角色模板
- 新任务模板
- 新规则方法库条目

注意，这里生成的是**候选项**，不是正式启用项。

### 5.4 第四步：进入审核

审核者可以是：

- 主人
- 管理员
- 产品或系统治理者

审核应重点判断：

- 这是不是高频真实需求
- 是否真的值得进入正式体系
- 风险是否可控
- 适合影响哪些角色和流程

### 5.5 第五步：验证与纳入

审核通过后，新能力仍不应直接全局开放，而应经过：

- 适用范围定义
- 角色绑定
- 质量验证
- 回退机制准备

之后再正式纳入系统。

## 6. 哪些内容适合增长，哪些不适合

### 6.1 适合进入受控增长的内容

1. **Skill 能力包**
   - 某类分析、抽取、整理、比较、沉淀能力

2. **角色模板**
   - 某类长期职责明确的新角色

3. **任务模板**
   - 某类高频专项流程

4. **规则方法知识**
   - 某类反复使用的定义、计算口径、检查框架

5. **沉淀升级策略**
   - 某类内容如何进入研究库、规则库、复盘库

### 6.2 不适合自动增长的内容

以下内容即使系统发现缺口，也不应进入自动增长区：

1. 用户核心观点
2. 用户正式纪律规则
3. 高风险执行能力
4. 影响交易行为的自动化权限
5. 会改变主权边界的系统能力

这些内容即使要变，也必须走更严格的确认和治理流程。

## 7. 和 Agent 团队的关系

### 7.1 Agent 团队负责“怎么协作”

例如：

- 哪些角色参与
- 各自记住什么
- 谁先做、谁后做
- 谁形成最终建议

### 7.2 受控 Skill 增长负责“能力怎么进入团队”

例如：

- 团队发现缺什么能力
- 这个能力是否值得正式加入
- 加入后给哪些角色用
- 是否进入某类任务模板

所以这两者不是重复关系，而是上下游关系：

- 团队是运行结构
- 受控增长是演进机制

---

## 8. 面向用户的产品表达建议

### 8.1 不要讲成“系统会自己长技能”

这种表达虽然很吸引眼球，但在投研场景里会带来两个问题：

1. 让用户误以为系统会无监督扩张。
2. 让用户对责任边界和可信度产生顾虑。

### 8.2 更适合的表达

前台更适合表述为：

- 系统发现了当前能力缺口
- 系统给出了补充能力建议
- 你可以审核是否把该能力纳入团队
- 审核通过后，团队能力会得到正式升级

这种表达更贴近产品真实边界，也更容易建立信任。

### 8.3 用户看到的应是“建议升级”，不是“已经自动升级”

这意味着前台更适合出现：

- 能力缺口提醒
- 升级建议卡
- 待审核能力项
- 已批准升级记录

而不适合出现：

- 系统已自动创建新 Skill
- 系统已自主替换团队配置

---

## 9. 建议的治理要求

### 9.1 所有正式能力升级都应可审计

至少应记录：

- 谁提出
- 谁审核
- 何时通过
- 适用于哪些角色和场景
- 版本号和变更说明

### 9.2 所有正式能力升级都应可回退

如果某个新 Skill 质量不足、边界不清或副作用过大，应能明确回退。

### 9.3 所有正式能力升级都应有限定范围

更合理的方式是：

- 先限定给特定角色
- 或限定给特定任务模板
- 或限定给灰度阶段使用

不要一上来全局放开。

## 11. 本文结论

对于 v4.0，建议判断如下：

1. **系统可以继续保留能力缺口发现能力**，这是智能化演进的重要基础。
2. **但系统不应走向无监督自主生成 Skill**，因为这会破坏可信边界和用户主权。
3. **更合理的方式，是建立受控 Skill 增长机制**：发现缺口、形成报告、提出候选项、进入审核、验证后纳入正式体系。
4. **增长的单位不只可以是 Skill，也可以是角色模板、任务模板、规则方法库和沉淀策略。**
5. **审核机制不是额外负担，而是投研场景下的可信度保障机制。**

因此，v4.0 更适合坚持这样一种进化路线：

**系统负责发现和建议，主人负责审核和批准，能力在受控、可追溯、可回退的前提下持续增长。**
