# v2.0 股票数据对接表

## 概述

本文档面向以下角色：

- 外部数据供应商
- 内部数据同步服务开发者
- 接口适配层开发者
- 数据库建模与 ETL 开发者

本文档回答的问题不是“分析要什么”，而是“对接时到底应该传什么字段、字段如何命名、哪些字段必须传、哪些字段可以缺省、如何映射到 v2.0 内部字段”。

建议与以下文档配合阅读：

- [docs/design/v2.0/v2.0-stock-data-requirements.md](docs/design/v2.0/v2.0-stock-data-requirements.md)

## 对接原则

### 1. 主键原则

建议所有股票类数据统一使用以下标识：

- 内部主键：code
- 可选兼容键：symbol

推荐规则：

| 场景 | 推荐值 |
|---|---|
| A 股内部主代码 | 600519 |
| A 股带交易所代码 | 600519.SH |
| 港股 | 0700.HK |
| 美股 | AAPL |

### 2. 日期原则

统一建议：

- 日期字段：YYYY-MM-DD
- 日期时间字段：ISO 8601 或可转为 datetime 的标准格式
- 交易日字段命名优先使用 trade_date
- 发布时间字段命名优先使用 publish_time
- 更新时间字段命名优先使用 updated_at

### 3. 数值原则

- 价格字段统一使用 number
- 百分比字段优先使用数值型，不带百分号
- 金额字段保持原始货币单位，不混入字符串单位
- 对于无法提供的数据，返回 null，不要返回空字符串伪装数值字段

### 4. 来源原则

所有可落库数据建议带 source 或 data_source 字段，用于多源优先级控制和问题排查。

## 四、基本面财务对接表

目标集合：stock_financial_data

### 4.0 评估结论

- 以 v2.0 当前主工作流而言，4.1 的必传字段已经可以支撑基础上线，属于最小可用集。
- 但如果希望同时满足股票详情页、智能筛选、后续研究增强和多源兼容，只有平铺摘要字段还不够，建议同步提交财务子表原始结构。
- 因此，对外对接时应区分两层交付：
  - 最小上线层：提交 4.1 必传字段，保证基本面分析师可运行。
  - 完整交付层：在 4.1 和 4.2 之外，同时提交 4.4 的财务子表原始结构，避免后续反复补字段。

### 4.5 原始结构交付规则

#### 4.5.1 主记录元信息

每条 stock_financial_data 记录建议至少带以下元信息：

| 字段 | 类型 | 是否建议 | 说明 |
|---|---|---|---|
| code | string | 是 | 主代码 |
| symbol | string | 建议 | 带交易所后缀代码 |
| report_period | string/date | 是 | 财报期 |
| report_type | string | 是 | quarterly / annual / semiannual 等 |
| ann_date | string/date | 强烈建议 | 公告日期 |
| data_source | string | 是 | 数据源标识 |
| updated_at | datetime | 强烈建议 | 最近同步时间 |
| currency | string | 建议 | 原始币种，跨市场时尤其重要 |

#### 4.5.2 结构规则

- 原始子表可以直接使用嵌套 JSON，不要求全部打平。
- 推荐结构为顶层摘要字段 + raw_data 子表字段并存，便于查询和回溯。
- 如果供应方没有 raw_data 容器，也可以直接提供 financial_indicators、balance_sheet、income_statement、cashflow_statement、main_business 这些一级嵌套对象。
- 同一条记录下的所有子表，应尽量对应同一 report_period；如果某个子表来自不同期次，需额外标明该子表自己的 period 字段。

#### 4.5.3 数值和口径规则

- 所有金额字段必须为 number，不带“万”“亿”“元”等单位文字。
- 百分比字段必须为数值，不带百分号；例如 18.5 而不是 18.5%。
- 如果是比例小数口径，需在 source 说明或字段说明中固定，不要同库混用 18.5 和 0.185 两种口径。
- revenue、net_profit、n_cashflow_act 等金额字段应尽量保持原始币种金额，不要混入展示格式。

#### 4.5.4 一致性规则

- 如果平铺字段与原始子表同时存在，应保证语义一致。
- 推荐优先级为：顶层摘要字段用于检索和筛选，原始子表用于回溯和补充分析。
- 如果 roe、gross_margin、debt_to_assets 等字段在顶层与 nested 中不一致，应以最新公告口径或供应方主口径为准，并避免同时保留两套冲突值。
- report_period、ann_date、report_type 在顶层与子表中如果同时存在，应保持一致。

#### 4.5.5 缺失容忍规则

- main_business 缺失，不影响 v2.0 P0 上线。
- financial_indicators、balance_sheet、income_statement、cashflow_statement 不建议长期缺失。
- 如果暂时无法提供全部字段，至少应保证每个子表交付其“必须建议”字段，避免只有空壳结构。

## 十一、验收清单

数据供应方完成对接后，建议按以下清单验收：

### 11.1 字段层验收

- 必传字段是否全部可用
- 数值字段是否为 number 而非字符串
- 日期字段格式是否统一
- code / symbol 是否统一规则
- source / data_source 是否可追踪

### 11.2 数据质量验收

- 是否存在大量 null 核心字段
- 是否存在 trade_date 断档
- 是否存在重复主键
- 是否存在 code 与 symbol 对不上的情况
- 新闻与社媒时间是否可排序

### 11.3 业务验收

- 能否支撑单股分析完整执行
- 能否生成市场分析报告
- 能否生成基本面分析报告
- 能否生成新闻分析报告
- 行业与大盘分析是否有足够数据支持

## 十二、推荐对接优先顺序

如果供应方能力有限，推荐按以下顺序逐步交付：

1. 股票主数据
2. 最新行情快照
3. 历史日线行情
4. 基本面财务
5. 新闻公告
6. 指数环境
7. 行业板块
8. 社媒情绪
9. 筹码分布

这个顺序可以保证 v2.0 先具备基础分析能力，再逐步补齐高阶判断能力。
