## 一、仍可能遗漏的问题清单

### 1. LLM 没走工具，直接口头提问

**场景**：
```
Nanobot："我建议方案 A，你觉得呢？"
```
如果这轮 LLM 没有调用任何工具（例如 `prepare_agent_requirement_intake`），Ledger 不会写入 `pending_question`。下一轮用户回复"可以"时，系统 prompt 里没有待确认上下文。

**缓解**：
- 每轮结束后**无条件**生成摘要（不依赖工具调用）
- 摘要内容从 `session.messages` 中提取，包含 assistant 的最后发言
- 摘要中明确标注"等待用户确认"

---

### 2. 摘要质量差，关键信息丢失

**场景**：
LLM 的长回复中包含了多个方案、多个问题，但自动摘要只抽了一句话，导致下一轮丢失细节。

**缓解**：
- 摘要不是简单一句话，而是结构化字段：
  ```json
  {
    "last_question": "我建议方案 A，保留 B 的灵活性，你觉得呢？",
    "pending_options": [
      {"id": "plan_a", "name": "方案 A"},
      {"id": "plan_b", "name": "方案 B"}
    ],
    "pending_decision": "等待用户选择方案",
    "current_stage": "exploring"
  }
  ```
- 摘要生成用专门的 prompt，要求保留关键决策点
- 摘要长度限制，避免污染 prompt

---

### 3. 多轮叠加后，摘要互相覆盖

**场景**：
第一轮问"用什么数据源"，第二轮用户没回答清楚，LLM 又问了"估值方法范围"。如果每轮只保留最近一轮摘要，第一轮的信息就丢了。

**缓解**：
- Ledger 中保留**所有 active 的待确认项**，不只是最新一条
- 注入 prompt 时列出所有未完成项：
  ```
  待确认事项：
  1. [上一轮] 数据源偏好：...
  2. [本轮] 估值方法范围：...
  ```
- 用户回复时，LLM 需要判断用户在对哪一项回复

---

### 4. 用户回复含糊，LLM 判断错误

**场景**：
```
Nanobot："我建议方案 A，你觉得呢？"
用户："可以"
```
LLM 看到"可以"，可能直接推进，而不是确认方案 A。

**缓解**：
- 系统 prompt 明确规则：
  ```
  如果用户回复"可以/好的/没问题"，且当前有待确认项，视为对最近一个待确认项的认可。
  不要重新开始对话，不要反问"你指的是什么"。
  ```
- 同时注入最近几轮 messages，让 LLM 看到完整上下文

---

### 5. 阶段判断错误

**场景**：
用户说"确认"，LLM 应该调用 `prepare_agent_generation_confirmation` 进入需求确认阶段。但如果摘要中没有明确"当前阶段"，LLM 可能继续停留在 exploring。

**缓解**：
- 摘要中必须包含 `current_stage`
- FlowController 仍然保留，根据 `thread_context.intent.stage` 注入阶段约束
- 摘要和 FlowController 双重约束，避免 LLM 跳阶段

---

### 6. 工具调用结果进入摘要，但语义不对

**场景**：
工具返回了一大段 JSON 或错误信息，自动摘要生成器错误地把它当成"当前待确认事项"。

**缓解**：
- 摘要生成时过滤 tool result 消息，只提取 assistant 的发言和关键工具结论
- 对 tool result 做结构化解析，而不是直接塞原文
- 摘要生成后加校验规则（不能包含 tool_call_id、不能超过长度）

---

### 7. 长对话超出 context window

**场景**：
多轮 Agent Builder 对话后，messages 越来越长，加上摘要、flow guidance、工具 schema，最终超出模型 context window。

**缓解**：
- 引入 context compression：中间轮次摘要压缩，保留最近 N 轮完整对话
- 使用长上下文模型（如 128k）作为 Nanobot 后端
- 定期清理 session 中的工具结果，只保留结论

---

### 8. 多个 Agent 在同一线程讨论

**场景**：
用户在一个线程里先讨论 Agent A，然后转到 Agent B。Ledger 按 `spec_id` 隔离，但 LLM 可能混淆。

**缓解**：
- 每次切换 Agent 时，强制清空当前 thread 的 `pending_options`
- 注入 prompt 时明确"当前 Agent"和"之前讨论过的 Agent"
- 用户提到其他 Agent 时，先确认再切换

---

### 9. 摘要生成失败或耗时过长

**场景**：
每轮都调用 LLM 生成摘要，增加一次 API 调用，延迟上升，或失败时本轮没有摘要。

**缓解**：
- 摘要生成异步化，后台写入 Ledger，不阻塞主响应
- 失败时使用 fallback 摘要（从最近 assistant message 提取第一句话）
- 缓存摘要结果，避免重复生成

---

### 10. LLM 忽略系统 prompt 约束

**场景**：
即使注入了摘要、flow guidance、硬规则，LLM 仍然"失忆"或"乱猜"。

**缓解**：
- 这是 LLM 本身的不可靠性，无法 100% 消除
- 多重约束：摘要 + flow guidance + 硬规则 + 最近 messages
- 关键决策点强制走工具（例如方案选择必须调用某个工具记录）
- 用户回复确认时，让 LLM 必须调用 `prepare_agent_requirement_intake` 更新状态

## 二、问题的根因分类

| 根因 | 对应问题 | 解决难度 |

| LLM 不可靠性 | 4, 10 | 高，只能降低概率 |

| 工具调用不是强制的 | 1, 5 | 中，可通过规则约束 |
| context window 有限 | 7 | 中，需要 compression |
| 多 Agent 隔离 | 8 | 中，需要业务规则 |
| 摘要生成开销 | 9 | 低，可异步化 |

---

## 三、结论

**Ledger + 摘要能解决 60-70% 的跨轮上下文问题，但不能完全消除。**

剩下的 30-40% 来自：
1. LLM 本身的不稳定性
2. 摘要质量无法 100% 保证
3. 工具调用不是强制的，口头提问容易丢失上下文
4. 长对话后的 context window 压力

**要真正稳定，还需要：**
1. 关键决策点强制走工具，而不是让 LLM 口头确认
2. 摘要结构化，而不是自由文本
3. 多轮未完成事项累积，而不是只保留最新一条
4. 引入 context compression
5. 接受 LLM 仍有小概率出错，设计快速纠错机制
