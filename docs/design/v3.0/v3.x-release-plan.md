## 文档信息

| 项目 | 内容 |
| --- | --- |
| 视角 | 产品经理视角 |
| 日期 | 2026-05-11 |
| 适用范围 | 将当前过宽的 v3.0 功能集合拆分为多个可发布的小版本 |
| 参考依据 | `implementation-status-report.md`、`v3.0-acceptance-checklist.md`、`v4.0/v3-to-v4-feature-triage.md` |

## 一、为什么要拆分 v3.0

从产品经理视角看，当前 `v3.0` 实际上混合了 5 类不同产品：

1. 面向终端用户的投研助手。
2. 面向高频使用者的跟踪闭环与提醒系统。
3. 面向专业用户的数据源增强能力。
4. 面向外部集成方的开放接口能力。
5. 面向内部团队或高级运营者的 Agent / Workflow / Skill 平台能力。

如果把这些能力一起作为“v3.0”对外发布，会同时出现 4 个问题：

1. 发布叙事不清楚，用户听不懂产品到底先解决什么问题。
2. 验收范围过宽，任何一个高复杂度模块都可能拖慢整体发布。
3. 目标用户混杂，普通投资者、专业用户、集成方、内部运营团队的需求被放进同一个版本。
4. 支持和运维成本过高，产品团队很难在首发阶段同时支撑这么多入口。

因此，当前更合理的做法不是继续扩大 `v3.0`，而是把它重构成一个 `v3.x` 连续发布计划。

## 二、拆分原则

### 2.1 一个版本只讲一个主故事

每个小版本只允许有一个主卖点，最多带一个辅助卖点。

错误做法：

- 同时讲“智能助手 + QQ 机器人 + MCP + QMT + Agent 工坊”。

正确做法：

- 先讲“研究助手能不能帮你完成从问题到报告的闭环”。

### 2.2 一个版本只服务一类核心用户

每个版本必须明确“谁最先受益”：

- 普通投研用户。
- 高频跟踪用户。
- 专业数据用户。
- 外部集成方。
- 内部运营 / 产品团队。

如果一个版本同时面向以上多类用户，通常意味着范围还没收住。

### 2.3 先发布高频主链路，再发布低频平台能力

优先级应该是：

1. 高频使用且最容易感知价值的能力。
2. 能形成留存和复访的能力。
3. 专业增强和覆盖能力。
4. 平台型、构建型、运营型能力。

这意味着 Agent 工坊、Skill 自动生成、AI 工作流架构师虽然先进，但不应该先于核心用户链路成为外部发布主角。

### 2.4 已实现不等于该先发布

有些模块虽然已经实现度很高，但用户价值密度不一定高。

典型例子是 `MCP Server`：

- 从工程实现看，它已经比较完整。
- 从产品排序看，它依然应该晚于核心投研主链路，因为它服务的是少数集成方，而不是大多数首批用户。

### 2.5 Patch 版本只做修复，不再塞新主题

建议采用以下节奏：

- `v3.0.0 / v3.1.0 / v3.2.0 ...`：新主题版本。
- `v3.0.1 / v3.1.1 / v3.2.1 ...`：稳定性修复、体验微调、文档补齐。

不要把新能力混进 patch 版本，否则版本认知会再次失控。

## 三、建议的 v3.x 发布顺序

## 3.1 总体顺序

建议采用 5 个小版本逐步释放：

1. `v3.0.0` 核心投研助手版
2. `v3.1.0` 跟踪闭环版
3. `v3.2.0` 专业数据增强版
4. `v3.3.0` 开放集成版
5. `v3.4.0` Agent 生产力内测版

这个顺序不是按技术模块排列，而是按“用户价值显著度 + 交付风险 + 支持成本”排序。

## 3.2 目录落位

为避免后续文档继续堆在同一个 `v3.0` 目录中，建议按小版本拆目录：

- `v3.0.0`：继续使用 `docs/design/v3.0/`
- `v3.1.0`：使用 `docs/design/v3.1/`
- `v3.2.0`：使用 `docs/design/v3.2/`
- `v3.3.0`：使用 `docs/design/v3.3/`
- `v3.4.0`：使用 `docs/design/v3.4/`

对应验收测试计划文档：

- `docs/design/v3.0/v3.0.0-acceptance-test-plan.md`
- `docs/design/v3.1/v3.1.0-acceptance-test-plan.md`
- `docs/design/v3.2/v3.2.0-acceptance-test-plan.md`
- `docs/design/v3.3/v3.3.0-acceptance-test-plan.md`
- `docs/design/v3.4/v3.4.0-acceptance-test-plan.md`

## 四、分版本发布计划

| 版本 | 发布主题 | 目标用户 | 发布目标 | 建议发布形态 |
| --- | --- | --- | --- | --- |
| `v3.0.0` | 核心投研助手版 | 普通用户 / 首批付费用户 | 让用户完成“提问 → 选股 → 分析 → 看报告 → 加入跟踪”主链路 | GA |
| `v3.1.0` | 跟踪闭环版 | 高频使用者 / 老用户 | 让用户形成“跟踪 → 提醒 → 复盘 → 计划”的复访闭环 | GA |
| `v3.2.0` | 专业数据增强版 | 专业用户 / 高阶 A 股用户 | 强化数据深度和标的覆盖能力 | ETF GA + QMT Beta |
| `v3.3.0` | 开放集成版 | 开发者 / 外部集成方 | 提供受控的对外接口接入能力 | Beta 或定向开放 |
| `v3.4.0` | Agent 生产力内测版 | 内部团队 / 小范围客户 | 验证 Agent / Workflow / Skill 平台的生产效率价值 | Private Preview |

## 五、每个版本具体放什么

### 5.1 `v3.0.0` 核心投研助手版

**版本定位**：先把产品做成一个“能真正帮用户开始研究”的助手，而不是一个功能堆栈。

**建议纳入功能**：

1. 智能助手基础能力：线程、历史、摘要、用户画像、RAG。
2. 智能选股主链路。
3. 分析触发、报告查询。
4. 自选股管理。
5. 基础研究工作台体验。

**建议不放入此版本主叙事**：

1. QQ Gateway。
2. MCP Server。
3. QMT / ETF。
4. AI 工作流架构师。
5. Agent 工坊。
6. Skill 自动生成。

**为什么先发这个版本**：

1. 这是最容易让用户立即感知价值的链路。
2. 也是最接近“产品是什么”的核心叙事。
3. 它的用户学习成本最低，最适合首发建立口碑。

**发布门槛**：

1. 首次使用用户可以在一次会话中完成“提问 / 筛选 / 发起分析 / 查看报告 / 加入跟踪”。
2. 助手线程、摘要、报告引用没有明显断链。
3. 智能选股结果能稳定进入后续分析流程。

---

### 5.2 `v3.1.0` 跟踪闭环版

**版本定位**：让产品从“能用一次”升级到“愿意持续回来用”。

**建议纳入功能**：

1. 定时分析。
2. 统一通知中心。
3. QQ Gateway 与 IM 推送。
4. 持仓分析。
5. 交易复盘。
6. 投资计划。

**建议不放入此版本主叙事**：

1. MCP Server。
2. QMT / ETF。
3. AI 工作流架构师。
4. Agent 工坊。
5. Skill 自动生成。

**为什么排在第二个版本**：

1. 它解决的是留存问题，而不是首次理解问题。
2. 只有在 `v3.0.0` 先证明“研究入口成立”后，跟踪闭环才有意义。
3. QQ 和通知能力更适合作为增强闭环，而不适合作为首发卖点。

**发布门槛**：

1. 定时分析可稳定创建、暂停、恢复。
2. 站内通知和 QQ 推送具备一致性。
3. 持仓、复盘、投资计划至少能支撑基础使用场景，而不是只停留在"能调接口"。

**当前状态（2026-06-03）**：

1. 六大功能模块（定时分析、持仓分析、交易复盘、投资计划、通知中心、QQ Gateway）**全部已实现**。
2. 验收测试计划已编写：`docs/design/v3.1/v3.1.0-acceptance-test-plan.md`。
3. 功能概览已编写：`docs/design/v3.1/v3.1.0-feature-overview.md`。
4. QMT 增强部分工作（涨跌停统计、成交额排名、盘后降级、交易时段判断）已提前完成，属于 v3.2.0 前置项。
5. **待完成**：按验收计划执行验收测试，确认全链路通过后即可 GA 发布。

---

### 5.3 `v3.2.0` 专业数据增强版

**版本定位**：服务更专业、更看重数据完整性与覆盖能力的用户。

**建议纳入功能**：

1. QMT 配置、连接测试、基础 / 历史 / 财务同步。
2. QMT 大盘 / 板块 / 个股分析模式切换。
3. ETF 数据同步。
4. ETF 基础分析工作流。

**建议发布方式**：

1. ETF 相关能力可按 GA 发布。
2. QMT 建议先按 Beta 发布，因为环境依赖和安装门槛更高。

**为什么不提前到 `v3.0.0`**：

1. QMT 是强环境依赖能力，不适合当首发门面。
2. ETF 虽然重要，但更适合作为市场覆盖增强，而不是产品主入口。
3. 如果过早把专业数据能力提前，会显著增加客服、实施和环境支持压力。

**发布门槛**：

1. QMT 配置测试和同步任务成功率达到可运营水平。
2. ETF 从数据同步到分析结果链路闭合。
3. 环境依赖、使用前置条件和常见失败原因必须文档化。

---

### 5.4 `v3.3.0` 开放集成版

**版本定位**：把产品从“用户自己用”扩展到“可被外部系统调用”。

**建议纳入功能**：

1. MCP Server 6 个工具。
2. API Key 认证。
3. 每日配额控制。
4. 基础集成文档和示例。

**建议明确不纳入**：

1. 把 MCP 当作产品主入口宣传。
2. MCP 数据源治理的完整扩展。
3. 飞书 / 钉钉等多通道大规模扩张。

**为什么放到 `v3.3.0`**：

1. 它对外部集成方有价值，但对普通用户不是首要价值。
2. 它会带来明显的认证、配额、支持和兼容成本。
3. 从 PM 视角，它更像“开放能力层”，不应该抢在核心用户价值前面发布。

**发布门槛**：

1. 6 个 MCP 工具在标准场景下稳定可用。
2. API Key、配额、错误语义和文档一致。
3. 至少完成内部或定向客户试用，再考虑扩大开放。

---

### 5.5 `v3.4.0` Agent 生产力内测版

**版本定位**：验证系统是否具备“让团队更快构建 Agent / Workflow / Skill”的生产效率价值。

**建议纳入功能**：

1. AI 工作流架构师。
2. Agent 工坊。
3. Skill 自动生成系统。

**建议发布形态**：

1. 只做 `Private Preview` 或 `Admin Beta`。
2. 不建议直接面向所有用户公开。

**为什么必须最后放**：

1. 这是平台能力，不是首批用户的主价值。
2. 这类功能复杂度高、解释成本高、边界容易失控。
3. 目前 Agent 工坊的审批、灰度、生产反馈回流还没补齐，不适合直接当成熟产品发。
4. Skill 自动生成与工作流生成虽然能力强，但更适合作为内部提效工具，而不是首发市场卖点。

**发布门槛**：

1. 至少先在内部团队或少量客户中完成完整试用。
2. 版本构建、调试、评估、发布链路要稳定。
3. 必须明确哪些角色可用，哪些能力只限管理员。

---

## 六、哪些能力不建议继续塞进 v3.x 主版本

以下内容建议明确后置，避免再次把范围做大：

1. 回测服务：已明确移交到 `v5.0`。
2. 飞书 / 钉钉适配器：当前不是主交付重点。
3. Agent 发布审批、灰度发布、生产反馈回流：继续作为平台治理增强，不要混进公共版本承诺。
4. MCP 数据源完整治理：保留为后续基础设施工程。
5. 分层提示词完整对齐：继续作为质量工程推进，不单独包装成对外版本主题。
6. 协作运行时、动态产出、受控成长：优先作为底层增强，不要在前几次发布中讲成独立产品。

## 七、建议的发布时间窗

基于当前实现状态，建议采用“一个 minor 版本 + 一个稳定窗口”的节奏。

| 版本 | 建议时间窗 | 主要工作重心 |
| --- | --- | --- |
| `v3.0.0` | 2026-05 至 2026-06 | 收敛核心助手链路、压缩首发范围、做好验收和文档 |
| `v3.0.1` | `v3.0.0` 后 1-2 周 | 修复首发问题、补交互和文档 |
| `v3.1.0` | 2026-06 至 2026-07 | 建立跟踪闭环、通知和 QQ 场景 |
| `v3.1.1` | `v3.1.0` 后 1-2 周 | 修复推送、调度和数据一致性问题 |
| `v3.2.0` | 2026-08 | 推出 ETF + QMT 的专业数据增强 |
| `v3.2.1` | `v3.2.0` 后 1-2 周 | 修复环境配置与同步问题 |
| `v3.3.0` | 2026-09 至 2026-10 | 定向开放 MCP 集成能力 |
| `v3.4.0` | 2026-11 以后 | 以小范围内测方式验证 Agent 生产力能力 |

这个节奏的前提是：

1. 每个 minor 版本只引入一个主主题。
2. 每个 minor 版本后都预留修复窗口。
3. 平台型功能不要抢占公共版本发布时间。

---

## 八、最终建议

如果只保留一句话作为产品决策建议，那就是：

**先把 v3 做成一个“用户愿意持续使用的投研助手产品”，再逐步放出专业数据、开放集成和 Agent 平台能力；不要把所有已实现能力都塞进首发版本。**

更具体地说：

1. `v3.0.0` 只解决“能开始研究”。
2. `v3.1.0` 再解决“能持续跟踪”。
3. `v3.2.0` 再解决“数据更专业”。
4. `v3.3.0` 再解决“可以被集成”。
5. `v3.4.0` 最后才验证“能不能做成平台”。

这样拆分后，产品发布口径、测试范围、用户教育、运营支持都会清晰很多，也更符合当前项目的真实成熟度。
